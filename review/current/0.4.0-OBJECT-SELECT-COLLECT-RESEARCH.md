# SCAP-NG 0.4.0 — Object `select` and `collect` research

**21 October 2026 · Research recommendation only, not a schema decision or shipped grammar change.** Refs #248, #239, #232, #229.

## Recommendation

**Investigate removing *both* `object.select` and `object.collect` authoring wrappers**, not just `select`. Put native Object acquisition entities and parameters directly inside the `object` mapping; retain `filters`, `set`, traversal/behaviors and their precise pipeline semantics explicitly. No new optional synonym or second canonical grammar. A capability-specific schema must determine whether each direct key is a selector, acquisition setting or operation.

The terminology is a first-read problem: without specialist documentation, `select` and `collect` seem to do the same job. OVAL 5.12.3 distinguishes Object entities, collection behaviors, direct filters, and Set expressions, but **does not universally wrap Object entities in an element literally called `select` nor behavioral parameters in `collect`**. SCAP-NG's wrappers were introduced for classification. The distinctions must survive in native implementation and source provenance, not necessarily as author-visible wrapper names.

### Before (existing 0.4 Object declaration)

```yaml
capability: linux.partition
object: {select: {mount_point: {equals: /home}}}
```

### Proposed canonical authoring (research)

```yaml
capability: linux.partition
object: {mount_point: {equals: /home}}
```

```yaml
capability: windows.registry
object:
  hive: {equals: local_machine}
  key: {equals: 'SOFTWARE\Microsoft\Windows NT\CurrentVersion'}
  name: {equals: CurrentVersion}
```

```yaml
capability: independent.shellcommand
object:
  shell: powershell
  command: (Get-PnpDevice -class bluetooth -status OK).class
  error_if_exit_status_not_0: false
  error_if_stderr_exists: false
  filters:
    - include:
        stdout_line:
          field_requirement: at_least_one_exists_and_all_match
          case_insensitive_equals: Bluetooth
```

The Bluetooth `object.filters` example is *additionally* subject to the separate direct-Filter migration proof: native schemas today still require Set-operand filtering in some cases, and the converter inserts synthetic singleton Unions. The proposed absence of `collect` MUST NOT be treated as acceptance of direct Filter syntax or claim scanner parity.

## Evidence checked against versioned mappings

- [Supported catalog](../../schema/v0.4.0/capability-mappings/supported/README.md): inspected the `native.selector_map` fields for all **100** supported mapping JSON files. **77** have declared selectors, while **23** have none. Thus a wrapper named `select` is not even meaningful for every capability (for example `independent.shellcommand` or `windows.wmi.query`).
- **Zero of the 100** selector-name lists intersected the sampled reserved generic Object-control-key set: `select`, `collect`, `set`, `filters`, `capability`, `object`, `object_title`, `traversal`, `behaviors`, `foreach`, `for_each`.
- The Windows cmdlet capability is a particularly important **real meaning collision**: its native OVAL-derived `collection_parameters.select` is a record of output properties to retain (PowerShell Select-Object behavior), *not* SCAP-NG's generic `object.select` selector wrapper. A flat, capability-scoped representation could expose the original `select` field without ambiguity, but **a mixed old/new dialect could not be inferred safely**. Versioned import is required.
- Sample cross-checks on 16 distinct capability mappings found no overlap between their declared selector names and `collection_parameters` names (including independent text/XML content, file hash, Windows cmdlet/WMI, NTUSER, Registry, RPMVerify, Unix file/process). **Full 100-capability selector-vs-parameter and reserved-key collision audit still required.**
- Capability-specified legal selector alternatives, null behaviors, parameter requirements and operation typing remain versioned contracts. Examples: `windows.registry` requires the `hive/key/name` selector family; `independent.textfilecontent54` uses either `full_path/pattern/instance` or `directory/name/pattern/instance`, alongside `ignore_case/multiline/singleline/item_creation` collection behaviors.

## Release gates before adopting the flattening

1. Mechanically audit **all 100** capability mappings for clashes among selector names, acquisition parameter names, traversal keys and reserved `filters`/`set`/`capability` metadata. If collisions exist, redesign deliberately; **do not create silent precedence**.
2. Preserve Object family alternatives, required versus optional settings, null and absent semantics, dynamic Variables and foreach lineage; reject unknown keys and incompatible mixed old/new nesting.
3. Implement a *versioned, invertible* old-to-new Object migration; compare independent YAML and JSON graphs, original source provenance and all 4,001 document closures. Unlike YAML flow-versus-block formatting, removing either wrapper **changes the JSON graph** unless the compiler explicitly normalizes it.
4. Confirm direct Filter position, include/exclude, source actual Set operations, nested operands, Item cardinality, incomplete collection and OVAL six-state results before marking semantic parity.
5. Keep scanner-facing Object IR classified as **selector / acquisition parameter / post-collection Filter / Set**, irrespective of author-facing notation. Do not infer scanner semantics by flattening arbitrary mappings.
6. Show representative whole-Test examples (Linux mount, Registry, textfilecontent54 with behavioral flags, Windows cmdlet with native `select`, WMI, filtered shellcommand, nested Set), including examples that should be rejected.

**Decision status:** strong recommendation to prototype **no `select` or `collect` wrappers in new authoring**, conditional on collision audit and source/result equivalence; official schema and released artifacts unchanged.
