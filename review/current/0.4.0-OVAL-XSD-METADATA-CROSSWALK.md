## Metadata design decision

The normative JSON Schema retains machine-readable names and defines `title`/`description` at each operation/property site. Display tools shall use this metadata, including capability-native schema annotations, with version pinning. User-visible text is explanatory, not a substitute for OVAL conformance or a license to reinterpret results.

Do **not** copy OVAL's optional defaults: NG requires explicit Item existence. Do **not** assume translated titles prove semantic preservation. Additional native capability schema enumeration/field audits and all six-state conformance cases remain required before final release.

## OVAL Windows NTUSER documentation disposition (2026-10-20)

Owner-raised concern: the official OVAL 5.12.3 Windows system-characteristics
[`ntuser_item` definition](https://github.com/OVAL-Community/OVAL/blob/v5.12.3/oval-schemas/windows-system-characteristics-schema.xsd)
contains extensive scanner-developer material. Do not indiscriminately embed that
material into generated 0.4.0 JSON Schema `description` values.

**Schema includes:** concise `title`, `description`, authored property/types,
selectors, meaningful required/optional/nullable status and allowed operations.
**Normative capability specification includes:** collection scope, Item identity,
status handling, and evidence inclusion/exclusion behavior that affects test
results; preserve the OVAL-defined distinction between per-user registry items
and ordinary machine Registry items.
**Scanner guide includes:** suggested Windows Registry APIs; how to locate
profiles from ProfileList and ProfileImagePath; online HKEY_USERS and offline
NTUSER.DAT reading techniques; safe file handling and avoiding locks that
interrupt user logon; operational performance choices. Those are OVAL's
recommended implementation methods, *not* a mandatory OS API sequence.
**Provenance links:** cite the pinned XSD element, tag, and hash from the
capability specification or docs. Do not duplicate entire upstream annotations
across generated schemas or present source recommendations as normative mandates.

A subtle requirement: OVAL's recommended human-profile filtering is intertwined
with the semantic question of which users are in scope. Define the expected user
population explicitly in the capability contract. Do **not** assume that
following a sample SID regular expression is equivalent to all real local/domain
profiles, nor assert that alternative safe collection mechanisms are forbidden.

**Release audit:** before calling the NTUSER capability implemented, verify
collection scope; logged-on and logged-off users; permission and locked-hive
errors; absent profiles; optional/nil Registry value names; offline-access
failure; and Item identities. Scanner implementation-guidance text never counts
as proof that these conditions are tested.
