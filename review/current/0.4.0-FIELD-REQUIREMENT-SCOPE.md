# SCAP-NG 0.4.0 — field requirement scope: short decision packet

**Owner-approved naming direction, 2026-10-21; implementation not yet accepted.** No active schema, compiler output or published archive is changed by this decision. [Authoring audit #248](https://github.com/vanderpol/scap-ng/issues/248) · [Grammar gate #239](https://github.com/vanderpol/scap-ng/issues/239).

## The measured problem

After source-preserving AND/OR normalization, 231 ordinary unique-field groups are structurally reversible to `fields`: **184** declare a group-level field requirement; **44** inherit an explicit Test-level `state_fields_require`; **three** have only individual field requirements. **Thirty** other ANDs combine *separate original OVAL States* and must stay whole-condition ANDs; 25 would collide on field names and five on nested condition keys. The 231-group proof is structural/source-inverse evidence, not native XML or scanner-result parity.

OVAL has distinct Test `check_existence`, Test `check`, Test `state_operator`, State `operator`, and entity-level cardinalities. A YAML `fields` map can represent *one* original State-sized condition, not arbitrary flattening across original States.

## Approved spelling: `field_requirement` at every scope (schema integration pending)

```yaml
require:
  items: one_or_more
  field_requirement: at_least_one_exists_and_all_match
  all_items_must:
    - or:
        - fields:
            type: {equals: string}
            value: {equals: Enterprise}
        - field_requirement: may_be_absent_and_all_match
          fields:
            type: {equals: string}
            value: {equals: EnterpriseS}
```

**Inheritance rule for schema documentation:** A `field_requirement` defined at the Test's `require` level **applies to every field in every governed condition**, including all branches of `and`/`or`/`one`/`xor`, unless explicitly overridden closer to that field. A `field_requirement` on a logical group applies to **all descendant fields in that group** unless overridden by a nested group, complete condition, or individual field. A `field_requirement` immediately before `fields` applies to **all fields within that condition**, but not sibling conditions; an individual field's `field_requirement` overrides that inherited value **for that field only**. The nearest explicitly declared requirement wins. No implicit default is invented if no valid declaration is present. `require.items` separately controls **collected Item existence**, not field existence or matching. The outer `or` joins **complete conditions for each Item**, not the Items themselves.

**Suggested schema descriptions (to be copied into the normative version when promoted):**

- **Test-level `require.field_requirement`:** "Applies to all fields evaluated by this Test, including fields in nested conditions, unless a nearer `field_requirement` explicitly overrides it."
- **Logical-group `field_requirement`:** "Applies to all descendant fields of this logical group, unless overridden by a nested group, complete condition or individual field."
- **Condition-level `field_requirement`:** "Applies to all fields listed under this condition's `fields`, except fields with an explicit individual `field_requirement`; sibling conditions are unaffected."
- **Individual-field `field_requirement`:** "Overrides any inherited requirement for this field only; other fields continue to inherit their applicable requirements."

Precedence, from lowest to highest: Test → enclosing logical group(s) → complete `fields` condition → individual field. This applies only to field matching and presence, never Item quantifiers, record-member cardinality or other independent OVAL scopes.

Do not introduce an unwritten evaluator default: if a field does not have a local setting, one must be explicitly inherited from a valid enclosing scope, or the source must have a compatible source-exact representation. Any scope that lacks a documented explicit requirement must fail validation rather than silently assume a matching policy. Per-field overrides and OR/ONE/XOR or record behavior need their own conformance tests.

### Why not `override_fields_requirement`?

The word `override` describes a **relationship**, not the property's meaning. The very same declaration could be used as an independent local requirement when no Test-wide default exists; then `override_fields_requirement` would be misleading. It also requires a second spellable key and special validation rule. One consistent `field_requirement` name at Test, condition and individual field scopes is easier to search, teach, autocomplete and validate. A nearby declaration overrides a farther one by explicitly documented scope, rather than by magic keyed to the word `override`.

`field_requirement` (singular) is intentional: this is **one rule applied to each governed field's observed values**, not a new list of expected field names. It is more descriptive than bare local `require` and more idiomatic than `fields_require` or `fields_requirement`. It should NOT be renamed to `requirement` or `requirements`, which also describe a STIG Rule's policy requirement.

### Compared alternatives

| Option | Readability | Recommendation |
| --- | --- | --- |
| **Same `field_requirement` key at all scopes** | Field semantics visible everywhere; applies with or without inherited default | **Owner-approved naming direction, pending validation** |
| `override_fields_requirement` locally | Announces an override but only works when a parent exists, creating separate spellings | Do not choose |
| Test `require.fields` + local bare `require` | Short, but different keys for the same field policy; ambiguous on first read | Superseded research proposal |
| Explicit `state` wrapper | Familiar to OVAL authors; adds indirection for ordinary conditions | Retain only if semantic boundaries demand it |

**Compatibility note:** Today's active 0.4.0 authoring still uses `state_fields_require` and, in appropriate places, per-field `require`. This owner-approved uniform spelling has **not been schema-accepted or converted**. Its leaf-level use is proposed, not evidence that existing per-field checks can be renamed mechanically. Existing scope-preserving candidates and immutable releases remain unchanged.

## Non-negotiable acceptance tests

1. Source-driven migration must preserve distinct OVAL States, repeated entity names, State OR/ONE/XOR, record scopes, variables and special `check` values. Never flatten the 30 original whole-State AND groups into `fields`.
2. Reject mixed historical `state_fields_require` and proposed `require.field_requirement` on the same Test; reject conflicting/missing scope, illegal repeated declarations, and mixed logical siblings. No hidden field cardinality default.
3. For Test-level `require.field_requirement`, verify that two or more conditions inherit exactly the same rule unless a nearer condition `field_requirement` overrides it; a field-level `field_requirement` affects only that field. Cover the existing source per-field `require` as a distinct migration boundary. Treat `require.items` as orthogonal.
4. Pass original XML→0.4→independent OVAL 5.12.3 XML graph comparison and schema validation, including multi-State AND/OR/ONE/XOR and record/repeated-field counterexamples.
5. Prove six-state outcomes with zero/one/multiple and incomplete Items, nonmatching/missing fields, unknown/error/not-applicable, and `entity_check`/`var_check`; validate six-STIG YAML/JSON plus typed graph under a candidate-only schema before any promotion.
