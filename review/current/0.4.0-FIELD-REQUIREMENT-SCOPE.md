# SCAP-NG 0.4.0 — field requirement scope: short decision packet

**Review-only, 2026-10-21.** No active schema, compiler output or published archive is changed by this proposal. [Authoring audit #248](https://github.com/vanderpol/scap-ng/issues/248) · [Grammar gate #239](https://github.com/vanderpol/scap-ng/issues/239).

## The measured problem

After source-preserving AND/OR normalization, 231 ordinary unique-field groups are structurally reversible to `fields`: **184** declare a group-level field requirement; **44** inherit an explicit Test-level `state_fields_require`; **three** have only individual field requirements. **Thirty** other ANDs combine *separate original OVAL States* and must stay whole-condition ANDs; 25 would collide on field names and five on nested condition keys. The 231-group proof is structural/source-inverse evidence, not native XML or scanner-result parity.

OVAL has distinct Test `check_existence`, Test `check`, Test `state_operator`, State `operator`, and entity-level cardinalities. A YAML `fields` map can represent *one* original State-sized condition, not arbitrary flattening across original States.

## Candidate structure (not normative)

```yaml
require:
  items: one_or_more
  fields: at_least_one_exists_and_all_match  # proposed explicit Test-wide field policy
  all_items_must:
    - or:
        - fields:
            type: {equals: string}
            value: {equals: Enterprise}
        - require: may_be_absent_and_all_match  # explicit local override
          fields:
            type: {equals: string}
            value: {equals: EnterpriseS}
```

Here `require.items` applies only to the collected **Item population**. The **proposed** `require.fields` holds the current *explicit* Test-wide field-presence/matching policy (currently `Test.state_fields_require`). A preceding condition `require` overrides that policy only for its complete `fields` group; an individual field's `require` remains the narrowest override. The outer `or` joins two **complete conditions on each Item**, not Items themselves. No field requirement is inferred from omission, and an Item absence must not become an automatic PASS.

### Why not simply repeat local `require`?

The 44 Test-inherited groups are intentionally governed by one shared declaration. Copying its value into every branch adds authoring noise and creates divergent-update risk. The original current Test scope should instead remain explicit and machine-checkable when a scope-preserving new spelling is approved.

### Naming alternatives

| Candidate | Benefit | Drawback |
| --- | --- | --- |
| `require.fields` at Test + local `require` at condition (**research preference**) | No legacy `state` vocabulary; item and field cardinalities visibly distinct inside the same requirement declaration | `fields` has a scalar meaning under Test `require` and a predicate-map meaning in conditions; needs first-read validation |
| Test-level `fields_require` + local `fields_require` | Very explicit about field scope, minimal parser conceptual change | Redundant, less natural, and retains separate requirement vocabulary |
| Explicit `state` wrapper around each group | Faithful OVAL term and visibly bounded state | Adds a wrapper even to ordinary simple checks, without changing what is evaluated |

`requirement`/`requirements` are **not** proposed as alternate wire keys: they risk confusion with a STIG Rule policy requirement. This packet does not approve any of these spellings.

## Non-negotiable acceptance tests

1. Source-driven migration must preserve distinct OVAL States, repeated entity names, State OR/ONE/XOR, record scopes, variables and special `check` values. Never flatten the 30 original whole-State AND groups into `fields`.
2. Reject a Test with both historical `state_fields_require` and proposed `require.fields`; reject conflicting/missing scope and mixed logical siblings. No hidden field cardinality default.
3. For a Test-scoped requirement, verify two or more conditions inherit the same policy *unless locally overridden*, and leaf `require` overrides only its own field. Treat `require.items` as orthogonal.
4. Pass original XML→0.4→independent OVAL 5.12.3 XML graph comparison and schema validation, including multi-State AND/OR/ONE/XOR and record/repeated-field counterexamples.
5. Prove six-state outcomes with zero/one/multiple and incomplete Items, nonmatching/missing fields, unknown/error/not-applicable, and `entity_check`/`var_check`; validate six-STIG YAML/JSON plus typed graph under a candidate-only schema before any promotion.
