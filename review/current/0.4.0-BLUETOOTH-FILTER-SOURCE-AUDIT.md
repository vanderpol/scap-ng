# SCAP-NG 0.4.0 — Windows 11 Bluetooth Filter source-trace review

**2026-10-20 · Refs #229 #232 · Source-backed defect / candidate fix.** The current 0.4.0 ZIP remains unchanged. This page is a review packet, **not a new accepted source grammar**.

## Finding

The observed `condition.bluetooth-installation.assessment` contains a singleton `union` wrapping a command Object solely to attach an `include` Filter. This union **does not exist in the original OVAL 5.12.3 source**. It was manufactured by the 0.3 native converter and then carried forward unchanged into the 0.4.0 samples.

The exact source is the [NIWC Windows 11 V2R10 enhanced V18 SCAP 1.4 ZIP](https://github.com/niwc-atlantic/scap-content-library/blob/main/Current/U_MS_Windows_11_V2R10_STIG_SCAP_1-4_Benchmark-enhancedV18-signed.zip), Git blob SHA-1 `712cc3176b1e44616aaf2f3ba5e62b299ad0643c`; ZIP SHA-256 `e4b8d55b58aa80124bd0974977af4c7f7bde35c748e2940e02857419292d8c3d`. Actual XML and all referenced IDs were independently extracted by [focused CI](https://github.com/vanderpol/scap-ng/actions/runs/39484071509), not guessed from the converted Assessment.

## Original OVAL facts (source fragments)

One Test with **no State references**:

```xml
<ind-def:shellcommand_test id="oval:navy.navwar.niwcatlantic.scc.windows:tst:101"
  version="18" comment="Report true if bluetooth installed"
  check_existence="at_least_one_exists" check="all">
  <ind-def:object object_ref="oval:navy.navwar.niwcatlantic.scc.windows:obj:101"/>
</ind-def:shellcommand_test>
```

One command Object with an attached **direct** Filter. There is **no** `set` or `UNION` element in this Object:

```xml
<ind-def:shellcommand_object id="oval:navy.navwar.niwcatlantic.scc.windows:obj:101"
  version="18" comment="Run command: (Get-PnpDevice -class bluetooth -status OK).class">
  <ind-def:shell>powershell</ind-def:shell>
  <ind-def:command>(Get-PnpDevice -class bluetooth -status OK).class</ind-def:command>
  <oval-def:filter action="include">oval:navy.navwar.niwcatlantic.scc.windows:ste:101</oval-def:filter>
</ind-def:shellcommand_object>
```

Filter State:

```xml
<ind-def:shellcommand_state id="oval:navy.navwar.niwcatlantic.scc.windows:ste:101"
  version="18" comment="Check if Get-PnpDevice command returned any items with class 'Bluetooth'">
  <ind-def:stdout_line operation="case insensitive equals">Bluetooth</ind-def:stdout_line>
</ind-def:shellcommand_state>
```

Therefore the author-intended processing is **collect PowerShell command output → retain Items whose `stdout_line` satisfies the filter → check at least one retained Item exists**. The original Test `check="all"` is not a State comparison because there are no Test State references.

## Why the redundant wrapper appeared

The [existing converter](../../tools/scap_upconvert_v003/native_capability_mapping.py) contains an explicit `direct_filters` lowering: because 0.3 placed Filters only on Set operands, it replaced a directly filtered Object with `set: {operator: union, operands: [{object: original, filters: original_filters}]}`. The 0.4 schema [capability-common.schema.json](../../schema/v0.4.0/capability-common.schema.json) still defines `filters` only inside Set Object operands, and the [0.4 capability schema generator](../../tools/generate_capability_schema_v04.py) follows that restriction. The converter therefore preserved its own old workaround even though the original content was simpler.

The source shape **may be logically equivalent for a single filtered operand**, but that must include Item status, multiplicity, error/unknown, incomplete collection, `stdout_line` multivalue matching and original Filter-State non-Boolean handling—not merely the passing happy path. This particular source proves the Set is *invented*, not that the scanner has been semantically verified.

## Suggested direct 0.4 authoring form — proposal only, not valid under current native schema

```yaml
tests:
  report-true-if-bluetooth-installed-test:
    test_title: Report true if bluetooth installed
    capability: independent.shellcommand
    object:
      collect:
        shell: powershell
        command: (Get-PnpDevice -class bluetooth -status OK).class
        error_if_exit_status_not_0: false
        error_if_stderr_exists: false
      filters:
        - include:
            stdout_line:
              require: at_least_one_exists_and_all_match
              case_insensitive_equals: Bluetooth
    require:
      items: one_or_more

evaluate:
  test: report-true-if-bluetooth-installed-test
```

**This uses a proposed `object.filters` field.** It cannot be silently substituted into published 0.4 content or claimed to pass native 0.4 schema validation without extending the Test/Object and each generated capability schema. The explicit inclusion step must **not** be changed to an `all_items_must` compliance State: doing so would change the population being tested. OVAL shellcommand can represent a `does not exist` Item for absent stdout; the migration must preserve that status too.

## Corpus impact and guarded migration plan

[Six-source CI audit](https://github.com/vanderpol/scap-ng/actions/runs/39485257966) finds **36 candidate Test/Object instances** (not 36 distinct Assessments) with the converter-shaped singleton filtered-Union pattern across 4,001 documents. Of those, **28** have one uniquely matching original OVAL Object containing direct Filters with the same actions and **no Set**; eight require further source mapping, including reused shared Assessments and possible ambiguous source titles. The report and exact per-Object references are retained as GitHub Actions engineering artifacts.

A safe 0.4 fix should:

1. Specify direct Object Filters in both common and capability-specific 0.4 authoring schemas, with **identical Filter item-selection and error semantics** to the existing Set-operand Filter.
2. Upgrade only when source provenance proves the original had a direct Filter and no Set. Preserve legitimate multi-operand/nested Sets. Keep the exact native `include` or `exclude`, field predicates, Source Object/Test IDs and ordered Filter list.
3. Add inverse/recovery and six-state regression fixtures covering zero/one/multiple stdout lines, a nonmatching line, error/unknown, incomplete collection and missing/does-not-exist command Items. Do not infer `all_items_must`.
4. Regenerate YAML and JSON complete six-STIG content, validate all 4,001 files and 2,958 Rule-choice links, compare corrected output against original OVAL behavior, and release a **separately identifiable new sample revision**, preserving the existing ZIP/source hashes.

The remaining eight title-ambiguous instances must be resolved against source identities; do not bulk-rewrite them by structural similarity alone.

**Decision boundary:** The XML source diagnosis is confirmed. The new direct `object.filters` authoring grammar and runtime-parity proof are **not yet accepted/completed**.
