# SCAP-NG 0.4.0 — logical operators versus cardinality (review packet)

**Status:** owner-approved logical vocabulary direction, and preferred
`and/or/one/xor` are now accepted alongside deprecated source aliases
by the active 0.4.0 **expression and condition JSON Schemas**. The
full new-expression typed-source compiler rerun and runtime are separate
release gates; six-STIG migrated archives remain non-release candidates.
`fields`/local `require` naming is **NOT yet accepted 0.4.0 syntax**;
no Board ratification is inferred.
2026-10-21 · [Issue #248](https://github.com/vanderpol/scap-ng/issues/248)
and [scope issue #239](https://github.com/vanderpol/scap-ng/issues/239).

## The decision

Reserve **`and` / `or` / `one` / `xor`** for combining complete
logical outcomes. Reserve **`all` / `one_or_more` / `exactly_one` /
`none`** for quantifying *Items*, *field instances* or *Variable values*.
Operator names and quantifier names may produce the same six-state result
table when given identical nonempty results, but they **must not be freely
interchanged**, because they apply at different stages of OVAL evaluation.

This follows pinned upstream [OVAL common OperatorEnumeration and
CheckEnumeration](https://github.com/OVAL-Community/OVAL/blob/v5.12.3/oval-schemas/oval-common-schema.xsd)
and [OVAL TestType and StateType](https://github.com/OVAL-Community/OVAL/blob/v5.12.3/oval-schemas/oval-definitions-schema.xsd).
The official base Test XSD independently defines `state_operator`,
`check` and `check_existence`; StateType independently defines `operator`.

| Original OVAL level | Original 5.12.3 vocabulary | Proposed NG authored meaning |
| --- | --- | --- |
| Collected-Item existence | Test `check_existence` | `require.items` |
| How many collected Items match | Test `check` | explicit Item-matching quantifier; `matching_items` research candidate, not accepted syntax |
| Several referenced States on *each Item* | Test `state_operator=AND/OR/ONE/XOR` | `and` / `or` / `one` / `xor` **between complete conditions** |
| Several entity fields inside *one State* | State `operator=AND/OR/ONE/XOR` | `fields` represents **one** condition, common AND can be visually implicit; explicit `fields_operator: or/one/xor` for source exceptions |
| Field existence and entity values | `check_existence`, `entity_check`, `var_check` on State entity | `fields_require` group scope plus explicit narrower field/Variable overrides; cannot collapse independent cardinalities |
| Multiple Assessment Tests | OVAL Definition `criteria operator` | `assessment.evaluate` expression; not the per-Item State operator |

The normal `fields:` mapping would *explicitly be defined by the grammar*
to conjoin its entries (OVAL default State `operator=AND`); this is not an
undocumented evaluator default. A State with `operator=OR/ONE/XOR` needs an
explicit non-default field operator; never flatten it into Test alternatives.

## Real pinned OVAL example: two alternative complete States

Original [Windows `ntuser_test`](https://github.com/OVAL-Community/SCAP-Self-Assertion/blob/e3538595c5083b9c34d937a81d319234df9bbfaa/SCAP_1.4/OVAL_Test_Content/windows/win-def_ntuser_test.xml),
Test `oval:navy.navwar.niwcatlantic.scc.windows.test:tst:13`:

- `check_existence="at_least_one_exists"` — need collected Item(s);
- `check="at least one"` — at least one Item must match;
- `state_operator="OR"` — for **each** Item, it may match original
  `ste:13` (`account_type = domain`) **or** original `ste:10`
  (`account_type = local`).

Possible **review-only** compact rendering (not valid current 0.4.0 syntax):

```yaml
require:
  items: one_or_more
  matching_items: one_or_more
  conditions:
    - or:
        - fields_require: at_least_one_exists_and_all_match
          fields:
            account_type: {equals: domain}
        - fields_require: at_least_one_exists_and_all_match
          fields:
            account_type: {equals: local}
```

**Incorrect alternatives:** (a) one field `account_type` declared twice in a
YAML mapping (one branch disappears); (b) flatten `or` to *any Item* (moves
the operator to a different layer); (c) use `all_items_must` for this Test
(incorrectly changes `check="at least one"` into `check="all"`).

## Cross-state flattening can produce a false PASS

Two hypothetical OVAL States on each registry Item:

- A: `type=dword AND value=0`.
- B: `type=string AND value=Disabled`.
- Test `state_operator=OR`: **(A) OR (B)**.

An Item with `type=dword, value=Disabled` matches neither complete State.
The correct OR of the two State results is **false**. Flattening four
individual comparisons into a single OR would incorrectly pass it because
`type=dword` and `value=Disabled` are individually true.

## ONE is not XOR

For three true condition results, `one` yields **false**, while `xor`
yields **true** (OVAL XOR means *odd parity*). For two true conditions,
`or` yields **true**, but `one` yields **false**. Unknown/error/not-
evaluated/not-applicable must follow OVAL's six-state tables, not ordinary
Python Boolean shortcuts.

A real original State could also have `operator=OR`, which combines
**its fields**, rather than multiple States. Distinguish it from Test
`state_operator=OR` even where they happen to yield the same result.

## Naming review: State, fields_require, require, requirement, requirements

**Owner vocabulary exploration, 2026-10-21 — no schema promotion.**
There are *two separate naming decisions*. The first is what to call
the **one-State-sized group of expected fields**. The second is what to call
the **existence+matching quantifier inherited by those fields**. OVAL
`State` names the entire expected-condition node; `fields_require`
names the *cardinality setting*, not the node. Comparing them as
alternative key spellings would answer the wrong design question.

Current proposed verbose form (research-only):
```yaml
require:
  items: one_or_more
  all_items_must:
    - fields_require: at_least_one_exists_and_all_match
      fields:
        type: {equals: dword}
        value: {equals: 0}
```

Three genuinely different alternatives:

**A — preserve a visibly named OVAL State (strongest migration familiarity):**
```yaml
require:
  items: one_or_more
  all_items_must:
    - state:
        require: at_least_one_exists_and_all_match
        fields:
          type: {equals: dword}
          value: {equals: 0}
```
Pro: unmistakable node boundary and OVAL roundtrip. Cons: wrapper on every
simple policy, old OVAL term with technical baggage; State might be confused
with the observed system's actual state rather than a *desired condition*.

**B — explicit `fields_require` plus `fields` (clearest scalar scope):**
```yaml
require:
  items: one_or_more
  all_items_must:
    - fields_require: at_least_one_exists_and_all_match
      fields:
        type: {equals: dword}
        value: {equals: 0}
```
Pro: unambiguous that cardinality applies to fields, not Items or whole
conditions, and no extra `state:` wrapper. Cons: unidiomatic English,
verbose, overlapping `require`/nested `require`/STIG policy requirement.

**C — self-contained expected condition, generic scoped `require`
(preferred *exploratory* version):**
```yaml
require:
  items: one_or_more
  all_items_must:
    - require: at_least_one_exists_and_all_match
      fields:
        type: {equals: dword}
        value: {equals: 0}
```
Pro: shorter, same broadest-explicit-then-override principle as existing
field-level `require`, clear `fields` boundary for a logical condition.
Cons: `require` is also a Test-level property but refers there to Item
existence/matching; readers must understand *scope*, and the schema must
enforce that it cannot be confused with policy requirements or inherited
through a record. This is **not valid active 0.4.0 schema today**.

**D — `requirements` / `requirement` (possible but not preferred):**
```yaml
requirements:
  items: one_or_more
  all_items_must:
    - requirement:
        fields:
          type: {equals: dword}
          value: {equals: 0}
```
This sounds natural in English, but fails to say what is required about
observed field *presence, cardinality and matching*, and duplicates the
ordinary **STIG Rule policy requirement** concept. Without a separate
quantifier it loses required behavior; adding `fields_require` brings
back the original vocabulary burden. `requirements:` as a Test-level
rename of `require:` would also invalidate much currently versioned
authoring with little measurable gain. Use these terms for actual
policy requirements or explanatory/editor language, not a new OVAL
cardinality control without convincing first-read evidence.

**Measured impact on the latest six-STIG canonical JSON candidate:** the
independent authoring ZIP attached to [successful six-STIG
run 39503111241](https://github.com/vanderpol/scap-ng/actions/runs/39503111241)
contains **1,375 Tests**, with **816** structured `all_items_must` Tests,
**308** occurrences of `state_fields_require` (including **200**
`and`-wrapped groups), **172** Tests with source-preserving `states`,
and **128** with `states_match`. These are counts of locations, **not**
individual original OVAL States. This proves the scope/naming decision affects
actual generated authoring at material scale. A cosmetic global substitution
would not unify the two surviving semantic representations. In particular,
`SV-253254` has two complete source States combined with
`states_match: any`; do not drop that boundary when removing simple
field-level `and` wrappers. It is another reason to make a complete
condition boundary visible in the authored syntax.

**Recommended working hypothesis:** do not bring back `state` simply
to name field cardinality. Use a real `fields:` node (one original-State
sized condition) with a preceding locally-scoped `require:`, and
`fields_operator: or/one/xor` only for original exceptional State
operators. Between whole conditions, use explicit `and/or/one/xor`
as proven by OVAL six-state tables. Keep Item quantity in separate Test
`require.items` / matching cardinality. Explicit `require` per field
overrides the group. This hypothesis must first be tested by an unaided
auditor and by exact source→NG→source compatibility.

An alternative editorial compromise is **keep the machine-valid key
`fields_require` for now**, but have the editor label it
`Field existence and matching` and visually render one `Condition`
group (without exposing OVAL State IDs). This yields readability
improvement without a premature wire-format rename.

Avoid all syntax changes until a reviewed owner decision, versioned
migration, schema guard, and source-backed six-state conformance proof.
**Not a reason to edit the historic 0.4-A/0.3 branches or the published
0.4.0 release archive.**

## 2026-10-21 fields boundary census after the AND/OR candidate

The independent source-linked [read-only fields layout audit](../../tools/audit_v04_condition_fields_preview.py)

- **30 outer `and` groups** come from OVAL **Test**
  `state_operator=AND` of several complete States. They are explicitly
  **not** one State's field conjunction and must be kept as operators
  between conditions. **25** repeat a field key across State alternatives,
  and the other **five** repeat nested logical branch keys. A one-level
  `fields:` map must never absorb these.
- **231 structurally simple inner `and` field groups** have distinct
  field names: 184 carry a group-scoped existence/matching rule, 44 inherit
  a Test-level rule, and three have solely explicit per-field exceptions.
  These are *candidates* for `require + fields`, not 231 newly certified
  original OVAL State identities; source-relative State identity remains
  a separate before/after check.
- The source-independent readability recommendation remains: a **condition**
  contains a `fields:` map with a preceding local `require:`, whereas
  `and/or/one/xor` combine **whole conditions**. For repeated
  fields/complex source semantics retain a list- or named-condition
  representation; do not silently overwrite YAML mapping keys.
- The native 0.4.0 schema does not yet recognize `fields:` as an authoring
  grammar alternative. This is field-naming research, not a shipping change.

## Real six-STIG field-scope impact after AND/OR (naming decision only)

The [source-invertible fields preview](https://github.com/vanderpol/scap-ng/actions/runs/39593978798) safely rewrote **231** simple, ordinary within-State AND groups. An independent before/after census of the pinned JSON artifacts separates the **67 already-existing** `fields:` records from newly proposed `fields:` condition maps. Among **231 newly transformed** groups:

| Scope of field existence/matching in source | Groups |
| --- | ---: |
| Local State/group-level requirement (maps to preceding `require:`) | 184 |
| Inherited from Test-level `state_fields_require` | 44 |
| Explicit `require` on individual fields, no inherited default | 3 |
| **Total reversible groups** | **231** |

This count is **not** a census of every arbitrary OVAL State; the converter
deliberately excludes repeated field keys, nested complex expressions and
record predicates. The 67 preexisting `fields` wrappers often represent
records and are **not** evidence that a general scalar `fields` condition
is already accepted by the active schema.

**Consequence for vocabulary:** Locally scoped `require:` before `fields:`
is elegant in **184** straightforward groups and gives each expected
condition an obvious original-State boundary. But **44** source groups
inherit the same Test-level default. Requiring a new local `require` in
every group would add repetition and obscure that those 44 groups deliberately
share the same requirement. The long-term language should permit a clearly
declared *enclosing* field cardinality scope and local overrides; neither
introduce hidden defaults nor globally flatten State scope into Item scope.
The user-approved **logical** `and/or/one/xor` spelling is orthogonal to
this naming choice.

**Current recommendation:** accept `and/or` operator semantics first.
Use `fields` to mark one complete expected condition and `require` as its
local default where needed; continue source-compatible inherited scope
until a full explicit contract (including records and repeated entities)
is independently tested. Do not introduce unreviewed `requirements`
synonyms or silently remove source compatibility. **No schema promotion of
`fields`/generic `require` is implied.**

## Choices that still need human sign-off

1. Adopt `fields_require` (placed **before** governed `fields`) and
   `fields` as a named one-State boundary, or use a different spelling?
   The first-stage reversible `state_fields_require`→`fields_require`
   helper exists but **has not been promoted into official 0.4 schema**.
2. Does a single `fields:` mapping represent only *unique* entity names,
   with a list-of-entries variant when original OVAL repeats an entity?
   Reject duplicate YAML mapping keys, never silently overwrite.
3. Preserve `one` vs `xor` as distinct operators at **both** Test-State
   and within-State levels. Do we call these `one`/`xor` or make
   `exactly_one`/`odd` explicit only within a separate cardinality axis?
   Recommend the former for pure logical operators to mirror OVAL.
4. Keep a source-backed mechanism for exact Item matching `check` including
   `none satisfy`, `only one`, `at least one`, and `all`. Rewriting
   `states_match: any` to `or` is NOT a global text substitution.
5. Before promotion: source-derived positive/negative converters for
   Test-State AND/OR and field-level OR/ONE/XOR; complete six-state checks
   including empty/incomplete collections and record/variable entities;
   schema rejection of mixed old/new aliases; exact source reversal;
   representative six-STIG JSON+YAML validation and a reviewer approval.

**Rejected shortcuts:** replace every `any` with `or`; flatten
multi-State OR into field OR; use Item `one_or_more` as a Boolean OR; merge
`ONE` and `XOR`; treat only one State OR source observed as proof that
other legal source forms do not exist; publish unreviewed syntax as 0.4.0.

## 2026-10-21 executable original-OVAL field-group boundary pilot

**Research implementation, not a released syntax decision.** The
[reversible field-group projector](../../tools/preview_v04_oval_operator_field_groups.py),
[adversarial fixture tests](../../tools/test_preview_v04_oval_operator_field_groups.py)
and [source-pinned OVAL workflow](../../.github/workflows/v04-oval-boolean-scope-research.yml)
extend the earlier real Windows 11 `require + fields` pilot to the six
independent.shellcommand original-OVAL operator fixtures that were already
validated against the pinned 5.12.3 XSD.

The projection deliberately distinguishes these cases without guessing
`check` or `check_existence`:

| Original source scope | Preview spelling | Rule |
| --- | --- | --- |
| One State, AND over different entity names | `fields: {exit_status: ..., stdout_line: ...}` | The compact mapping itself signifies conjunction within **one** State |
| One State, OR/ONE/XOR over entities | `fields_operator: or/one/xor` with ordered `fields` list | Explicitly retains the *within-State* operator, with no accidental mapping overwrite |
| One State, repeated entity name | `fields_operator: and/or/one/xor` with ordered `fields` list | No duplicate YAML mapping keys, even when the source operator is AND |
| One Test, several referenced States | `and/or/one/xor` over **complete** field-group conditions | Does not merge entity predicates from different source States |
| Test `check` and `check_existence` | Unchanged separate `item_matching_oval` and `item_existence_oval` pilot slots | **No** mistaken conversion of Item quantity to logical OR |

Source example, original Test `state_operator=OR` (two complete States,
each with a single entity), is represented as:

```yaml
item_condition:
  or:
    - fields:
        exit_status:
          attributes: {datatype: int, operation: equals}
          text: "0"
    - fields:
        stdout_line:
          attributes: {operation: equals}
          text: Enabled
```

Here `attributes`/`text` are lossless **pilot payloads**, not a proposed
final authoring comparison grammar. The source graph retains OVAL Test and
State IDs and per-Test references in a separate inverse ledger. This
preserves the distinction between whole-State `or` and field-level
`fields_operator: or` even for a shared original State with several
consumers.

The source-focused regression exercises **576** combinations of the six
OVAL result values across these six independent XML fixture Tests (as well
as independent 12,432-vector generic operator/quantifier tests retained
elsewhere). It also rejects `any` as a field operator, detects original
`ONE` versus `XOR`, prevents different-State flattening, preserves two
instances of the same field name, and checks exact inverse graph identity.
A separate existing Win11 SV-253254 source-backed fixture shows the
`require` cardinality setting preceding `or` with two `fields` maps.

**Limits:** This pilot proves Test/State semantic **graph** reconstruction
and six-state operator tables, not byte-for-byte OVAL XML export,
field-presence/default correctness, per-entity `entity_check` or
`var_check` evaluation, scanner parity, collector failures, Item empty/
incomplete behavior, or full six-STIG field migration. Synthetic duplicate
field names are tested for structural retention only; this is not a claim
that a repeated shellcommand field has independently passed the OVAL XSD.
The official 0.4 schema, current converter, approved ZIP and normative
specification remain untouched.

**Working recommendation:** Complete logical scope separation is strong
enough to continue in a review candidate. Prefer `require` plus `fields`
for the simple authored condition and `fields_operator` only for genuine
within-State exceptions; do not add a `state` wrapper solely for the name.
A mass schema rename is still blocked on source-backed entity presence,
records/Variables, direct compiler acceptance and owner first-read approval.

Of the 231 field groups, the earlier independently classified census
identified **184** with local `state_fields_require`, **44** inheriting a
Test-level requirement and **3** whose predicates have explicit individual
requirements. In this pilot only, locally declared
`state_fields_require` becomes `require` **before** `fields`. A
Test-inherited requirement remains at Test scope rather than being silently
deleted or duplicated. Individual field overrides remain unchanged.
Ambiguous, repeated-name, record and other unproven field shapes remain
in their original authoring representation.

For **all 4,001** source documents, the builder verifies an exact
two-stage original JSON→logical scope→field layout→inverse original
semantic source graph. Separately it verifies each candidate JSON
document equals its YAML parse. Both complete candidate archives and a
per-document changed-site/source-hash ledger are attached under the
GitHub Actions artifact `v04-and-or-fields-six-stig-candidate-research`.
These archives are **research previews**: not the accepted 0.4 schema,
compiler-ready assets, the Board review ZIP or scanner results.

reversible structural projection. Human readability and operational
equivalence must still be independently assessed, including original
OVAL field-existence and multi-value/record semantics and source-to-XML
roundtrip. The six focused tests cover structural failures; they do not
establish all six-state runtime boundaries for all 231 real groups.
