# Full audit of published SCAP-NG Board Discussions (2026-10-09)

**Engineering inventory — not a voting ballot and not ratified.** This document preserves the disposition of every published P001–P058 question. The owner-facing [decision register](0.3-vote-shortlist.md) now maps **18 distinct candidate decision areas** (11 automated Assessment/OVAL-successor, 7 wider SCAP-NG integration) to implementation issues; **it does not propose publishing 17 simultaneous votes**. The earlier six-question list was too narrow.

## Inventory and participation

A read-only [GitHub Discussions GraphQL audit](https://github.com/vanderpol/scap-ng/actions/runs/37924122491) enumerated **61 Discussions** in two pages: **58** numbered P001–P058 proposals, one older canonical-JSON/Ansible research thread, one voting-integration test, and the default welcome Discussion. **None of the 61 has a comment.** No numbered proposal has any reaction; the only reaction is one thumbs-up on **[Discussion #33, the voting-integration test](https://github.com/vanderpol/scap-ng/discussions/33)**. A second [read-only issue-link audit](https://github.com/vanderpol/scap-ng/actions/runs/37925063595) verified that **none of the 58 published proposal opening posts links to a GitHub implementation issue**. Their source-document references are not a decision-to-implementation map. Thus nothing is ratified or endorsed by these posts. These engagement figures are a point-in-time GitHub snapshot, not a prediction of future involvement.

Other non-proposal posts:
- [#35 — Canonical execution JSON and multiple authoring presentations](https://github.com/vanderpol/scap-ng/discussions/35): older non-voting Ansible-adjacent research. The successor **P053** already treats it as historical; archive after cross-linking rather than soliciting a separate vote.
- [#33 — Voting integration test](https://github.com/vanderpol/scap-ng/discussions/33): test only, with one thumbs-up; safe to retire once verified.
- [#32 — Welcome](https://github.com/vanderpol/scap-ng/discussions/32): platform-created introductory thread; keep or archive depending on the desired top-level Discussion landing page.

**Disposition definitions:** *Working* = requirement or agreed design direction reflected in the current pre-alpha specification or tracked implementation; **not** proof of scanner/runtime conformance or Board approval. *Candidate* = distinct issue that may merit a new scoped Board vote after a current evidence packet. *Superseded* = earlier published wording inaccurate for 0.3; preserve history but never ask the Board to approve it unchanged. *Defer* = not needed for the initial 0.3 feedback pass.

## Mandatory corrections before any new Board invitation

1. The 0.3 source model in [selection and Filters](../../specification/assessment/selection-and-filters.md) embeds each Filter predicate at the Object/Set use site and each expected-state comparison at the Test use site. **P007 and P008 are not current 0.3 authoring**; reusing named States is not the default or a supported independent registry.
2. [Current 0.3 design](../../research/iterations/003/design/CURRENT-DESIGN.md) retains the inherited **narrow `if/then/else`**, while wider case/elseif remains out of scope. **P016 and P058 need narrower wording**.
3. [Results draft](../../specification/results/results.md) says the old `reported`/thin/full simplification still needs a Board decision, while [CHANGELOG](../../CHANGELOG.md) records normative thin/full profiles out. Treat this as a **source-of-truth conflict** pending V2; do not disguise it as a settled published standard.
4. Clarify that **A** in the vocabulary comparison is actual 0.3; **B/C are research-only and not proven semantically equivalent**. Do not let a readability vote overrule source-compatibility or the canonical typed model.
5. Older migration evidence is not a substitute for the six-state / full dependency preservation gate. In particular, real 65-benchmark coverage, Self-Assertion and differential runtime tests have independent status and must be reported separately.
