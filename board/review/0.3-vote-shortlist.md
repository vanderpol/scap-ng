# SCAP-NG 0.3 Board decision register — owner review

**DRAFT — not published as new votes; no Board approval inferred (2026-10-09).** This replaces the earlier six-choice shortlist with a broader **18-area candidate register**, rather than pretending that six open implementation preferences represent all governance questions. **Do not send seventeen votes to the Board at once.** We need a bounded initial round selected from this register, with separately reviewable decisions.

- **A0–A10:** automated Assessment / OVAL-successor technical decisions and technical feedback. Prioritize a manageable initial Board review; the list does *not* assert the Board formally governs the entire SCAP-NG project.
- **S1–S7:** wider SCAP-NG Benchmark/policy/manual/package governance. These may be advisory Board review rather than formal OVAL Board standards votes; decide ownership and timing before sending.
- **Decision ≠ implementation.** A ballot names the high-level choice; its linked GitHub issues govern the separate schema/specification, migration, results, validation and tooling consequences. A previously closed/implemented issue is *not* evidence of ratification.
- **Common invariant:** no allowed alternative silently changes supported SCAP 1.4/OVAL 5.12.3 source meaning, six-state truth, typed evidence/provenance or execution security. Unsupported/deprecated cases fail explicitly. This is an acceptance condition, not a voting option.

## What must be in every published GitHub Discussion

A concise opening post (ideally 150–250 words **excluding example/code**) SHALL identify:

1. **One decision**, its scope (automated Assessment successor or wider SCAP-NG integration), the current 0.3 position, and a genuine option to disagree/propose an alternative. Do not disguise settled project preference as Board adoption.
2. One realistic source-backed example or a single link to a compact before/after example. Explicitly mark research-only B/C syntax as not validated.
3. **Implementation traceability:** “Affected GitHub issues” with the exact issue URLs from the table, a **primary coordinating issue**, and any additional acceptance/validation issues. This is deliberately different from links to reference documents alone. Confirm each link still exists.
4. Explicit compatibility and result-semantics constraints and expected proof (one short sentence + a details link).
5. A nonbinding feedback/vote statement; no silent ratification by reaction counts. Board vote outcome, owner decision, implementation work, and conformance status are separately recorded.

**Example:** The embedded-predicate decision **A1** references [#208](https://github.com/vanderpol/scap-ng/issues/208) as coordinating implementation, [#165](https://github.com/vanderpol/scap-ng/issues/165) for private/local scope, and [#194](https://github.com/vanderpol/scap-ng/issues/194) for value-quantifier vocabulary. Approval would *not* automatically mean the runtime-equivalence gate in #208 is complete, nor reopen settled source changes without review. A proposal requiring new schema, converter and runtime behavior maps to their corresponding existing issues and test obligations; create new ones only for genuine missing work.
