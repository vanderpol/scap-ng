Individual proposal files are **versioned voting records**, not the recommended introduction to SCAP-NG. Start with **[SCAP 1.4 → SCAP-NG key changes](../SCAP-1.4-TO-SCAP-NG-KEY-CHANGES.md)** and the **[0.2.0 review checkpoint](../SCAP-NG-0.2.0-REVIEW-CHECKPOINT.md)**.

Use **[VOTES.md](../VOTES.md)** for the complete P001–P058 list and published GitHub Discussion links.

## Proposal groups

- **P001–P010:** governance, architecture, native capability design, Objects/Filters/Variables.
- **P011–P020:** evaluation, collection/reuse, applicability, invocation context, versioning.
- **P021–P027:** metadata, informational policy, Results, evidence, completeness.
- **P028–P035:** packaging, signatures/trust, weights, coverage.
- **P036–P046:** Profiles, Tailoring, Parameters, Organizational Input, groups, manual assessment.
- **P047–P052:** CPE/applicability, identity/extensions, migration defects, independent conformance.
- **P053–P058:** canonical execution representation, authoring views, alternate result encodings, semantic retention/deprecation, objectless capabilities, conditional-authoring scope.

## Versioning rule

Publication does not equal ratification. React to the Discussion opening post with 👍 Yes or 👎 No; comments explain a vote. If a proposal's substance changes, create a **new version and fresh vote**. Do not silently rewrite already published voting text to match later implementation.

The current working design may therefore be newer than background prose inside an earlier proposal. The proposal's yes/no question remains the record of what was asked; the current architecture summary is the source for present project status.

Eligibility, quorum, voting duration, abstention/conflict handling, and official disposition still require Board agreement before reactions are binding.
