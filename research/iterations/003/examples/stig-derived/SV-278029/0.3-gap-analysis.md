## Correction: reuse existing applicability content

The first draft unnecessarily embedded a WMI domain-role Test inside this Rule's Assessment. Actual converted Windows Server 2025 content already has a reusable `condition.windows-domain-member-server-or-domain-controller` Assessment, which includes domain member server / DC role recognition. This is referenced by `dependencies.domain-joined` and `evaluate.assessment`. A separate dedicated `local-pdc-emulator` Assessment remains necessary; existing `windows-domain-controller` is **not** proof of PDC Emulator ownership. Both dependencies must be resolved to current-format immutable package members, with the PDC one currently absent. Reuse reduces authoring noise and means the side-by-side assessment of 0.3 readability must compare against a realistic reusable baseline, not the deliberately bloated first sketch.

## What current 0.3 already expresses

- `tests:` with typed native `windows.wmi.query` and `windows.registry` collectors.
- Inline Objects and States with explicit capability, selectors, expected values, existence and quantifiers.
- `evaluate: {if, then, else}` nested expressions referencing named Tests.
- Declared typed Assessment input consumed directly by a State (`value: {input: ...}` is a documented design direction, but full execution remains unproven).

The 0.3-shaped file expresses the intended branching more verbosely than the readable strawman. **It is not a compliant implementation of the STIG** for the reasons below.

## Candidate focused spec evolution — NOT YET ADOPTED

1. Preserve typed native collection; offer a concise **`collect` binding surface** exposing semantic fields, with strict collector/capability contracts and stable evidence IDs. Do not introduce magical platform fields.
2. Permit a readable local **condition expression** over typed collected fields (e.g., `domain.joined && !domain.is_pdc_emulator`), with explicit six-state evaluation and no silent default.
3. Offer `in` only for typed scalar-to-set membership after exact comparison and quantifier equivalence is established; parsed peers require `all`/set membership explicitly.
4. Decide whether literal status outcomes such as `return: unknown` belong in conditional branches; avoid conflating `not_applicable`, `false`, and `not_evaluated`.
5. Consider whether generating local Object/State wrappers from typed collector bindings makes source authoring simpler without losing correctness. The current 0.3 representation is a proof pressure test for that proposal, not proof of permission to drop those wrappers.
6. Formalize input applicability by branch and publisher → Rule → Assessment → request binding; keep scoping to groups of hosts, not per-host duplication.

## Review gate

We should *not* replace the normative 0.3 schema immediately on the basis of a beautiful sketch. First build a validated typed Windows Time collection contract, prove branch outcomes and input authorization, and measure readability against this real 0.3-shaped candidate. If faithful executable content cannot be made as clear as the initial strawman, revisit the architecture before asking the Board to review it.
