### What each `from` / `must` file proves—and doesn't

The Windows password-policy example is a fuller **seven-Test** conversion that intentionally retains seven separately reviewed requirements over a single objectless system observation, including four ordered integer checks and three Boolean checks. Its names now come from meaningful source fields rather than truncating boilerplate OVAL titles. The IOS-XE example exercises five Tests with exact integer and string-pattern operators over the same observation.

The Linux SELinux example contains three original Tests sharing the same singleton collection; C names the observation once and keeps three `must` checks joined with an explicit `require: every` tree. For the macOS plist check, original OVAL declares one Test + one Object + one State; the new C representation contains the same file/XPath selector and requires **every eligible Item** to report `value_of: true`, with original at-least-one existence preserved by the C compiler. The original Test comment, exact Definition ID and pinned XML location are in each file header.

The source-independent C compiler enforces the supported field capability mappings and confirms the lowered typed Test preserves the selected source Test's selector, operation, value, existence and matching. It does **not** execute a target collector or prove every scanner/OVAL evaluation outcome. Other original constructs are deliberately rejected rather than lost; advanced source Set/Filter/Variable/foreach and most compound multi-Test Definitions still need authoring conversion.

### Short feedback that would actually help

Please focus on **whether the evidence being gathered (`from`) and the requirement (`must`) are immediately clear**, whether `any_item`/`every_item` is clearer than current OVAL `check_existence`+`check`, and whether any part appears to hide essential dataflow or ownership of values. For the complex Windows/Apache examples, consider whether observations and derived values meaningfully reduce mental effort. There is no 0.4-C schema freeze decision being requested.
