# SCAP-NG 0.4 — draft scope and promotion gates

**Status: owner-directed 0.4 design work, not a normative specification freeze or OVAL Board approval.** The active 0.3 schema and releases are preserved. This is the controlled handoff from the [three-benchmark research](HUMAN-VERBIAGE-PROPOSAL.md) into a *single standard* 0.4 authoring grammar. [Owner vocabulary issue #227](https://github.com/vanderpol/scap-ng/issues/227) · [full-corpus evidence #225](https://github.com/vanderpol/scap-ng/issues/225).

## Why a 0.4 draft is justified

A [strict source-lowering proof](https://github.com/vanderpol/scap-ng/actions/runs/38737558392) represented **921/921** automated-by-default Rules in RHEL 9, Windows 11, and Windows Server 2025; **942** selected automated/applicability Assessment files were analyzed, **930** re-expanded to identical parsed 0.3 documents, and **12** used a separately identified State-free matching normalization supported by the OVAL reference result model. Typed collection, source literal arrays, filters, references, nested record predicates, and odd quantifier pairs remained representable. **This establishes feasibility to draft, not conformance or approval.**

SCAP-NG is *pre-alpha; no SCAP-NG scanner exists*. Live-scanner differential testing is **not** a precondition for selecting or publishing the *draft authoring specification*. It becomes an implementation/conformance gate once an independent scanner or reference evaluator exists. We **do** require executable specification-level semantics and strict validation for every new language feature.

## In scope for the 0.4 authoring-language proposal

| Area | Proposed 0.4 contract | Validation |
| --- | --- | --- |
| **One authoring grammar** | Use *one versioned standard Assessment syntax*, not two parallel canonical/compact authoring dialects or undocumented shorthand | Reject mixed or undeclared legacy spellings in 0.4; convert 0.3 inputs explicitly |
| **Inline field name** | State entries name the actual observed field: `- owner_uid: {...}` instead of `- field: owner_uid; ...` | Preserve ordering, duplicate field expressions, AND/OR, observed field `value`, record fields and capability-specific allowed names |
| **Human requirements** | A single explicit `require:` carries observed existence and matching semantics at Test, field, record and nested record-field positions; provide intelligible names for exactly one, absent, none matching, optional, etc. | No hidden defaults, wrong-scope aliases or contradictory combinations; cover all migratable source pairs, including rare ones |
| **Comparator-as-key** | `equals: 0`, `matches_regex: '...'`, and the existing typed native operations as *keys*, with exactly one operator and a typed operand | No scalar-only restriction that forces a second language for arrays, Variables, Organizational Input, version/bitwise operators or records |
| **Explicit collection of operands** | Keep typed literal arrays embedded directly in Object selectors or State expectations as already accepted in 0.3 | Preserve independent `value_match`, datatypes and source OVAL `var_check` meaning |
| **Nested record semantics** | Apply the same named field and requirement grammar to Windows records; record and subfield quantifiers remain independent | Missing/unknown record fields retain reference semantics (including error) |
| **Lossless migration and provenance** | Compile each 0.4 Assessment into a deterministic explicit comparison/evaluation intermediate (0.3-equivalent where appropriate) and retain source trace | Explicitly classify exact structural conversions versus model-equivalent normalizations; fail on unsupported or uncertain cases |
| **Independent capability validation** | Complete 0.4 JSON Schema, capability-specific valid field and operation catalog, invalid/negative fixtures, meaningful error paths | No magic field names, inferential scanner behavior or silently optional quantifiers |

Proposed Test examples: `require: only_one_exists` for no-State checks; `require: only_one_exists_and_matches` for State-bearing checks. The five common pairs and rare names remain **candidate vocabulary requiring terminology review**; do not infer acceptance of all 20 generated labels. The single grammar SHALL provide an explicit, discoverable and semantically precise way to express every valid migrated quantifier pair.

## Preserved unchanged from 0.3

Benchmark → Rule → Assessment, publisher's `default_assessment_choice` and manual tailoring alternatives, `evaluate` trees, manual Assessment language, explicit applicability, `for_each`, complex Variables and Filters, dependency graphs, typed Organizational Input and provenance, `reported_elements` redaction, collection/results semantics, signed `.scapng` bundles, and runtime `value_match` independence.

**Do not treat 0.4 as permission to rewrite evaluation trees or convert legitimate native checks to shell commands/manual.** Such a fallback requires independent technical justification, not authoring language aesthetics.

## Explicitly out of scope for 0.4 design

- A second optional "compact" authoring dialect, backward 0.3 syntax compatibility in the **same** normative source grammar, undocumented shorthand aliases or inferred Test/State defaults.
- Replacing valid uncommon OVAL semantics by heuristic/complemented comparisons; generic negation of regex/WMI/record operations.
- Shared Observation runtime/result semantics, major `evaluate` redesign, general new conditional language, runtime collection caching/reuse behavior, signed results/TPM details, or scanner implementation.
- Editor GUI and full Self-Assertion execution automation (separate later milestones); Solaris/macOS shell-heavy content does not drive grammar decisions.
- Changes to existing 0.3 schema, published Board Discussion #213, or already distributed content ZIPs.

## Gate definitions

1. **Draft gate — begin now:** One explicit grammar proposal; normative-voice requirements held in *research* until reviewed; standalone candidate schema/test fixtures; real RHEL9/Win11/Server2025 examples; owner reviews vocabulary and odd cases.
2. **Semantic gate — required before promotion:** All source-exact transformations verified; State-free normalizations prove OVAL 5.12.3 six-valued outcomes (including zero/unknown/error/incomplete/not-applicable); rare native record/Test cases remain unchanged unless independently proved equivalent.
3. **Schema gate — required before 0.4 checkpoint:** A **complete, independent `schema/v0.4.0/` snapshot** of the previous schema, version-consistent IDs/refs/metadata/mappings. Strong capability-aware validation, rejection tests, conversion round-trip and documentation links.
4. **Representative integration — required before owner review:** The six anchor STIGs including Oracle Linux 9, DNS and Apache; evidence of actual authoring simplification, complexity and losslessness. Limit frequent regression to focused/fast suites.
5. **Full corpus — at intentional release/Board checkpoint only:** Account for all 65 source packages, keep four known SQL-extension blockers visible, and [resolve converter regression #226](https://github.com/vanderpol/scap-ng/issues/226) before claiming a **current-main conversion release**.
6. **Later scanner gate, not a 0.4 authoring gate:** An independent implementation tests collected Items, unknown/error conditions, redaction, scanning and Self-Assertion; no claim of vendor conformity based on schemas alone.

## Decisions intentionally still open

- Final *human* names for rare combinations, including `optional`, `match: none`, exact-one and State-free presence; avoid blindly standardizing 20 awkward concatenated labels.
- Whether each `require:` should be a single English token or a carefully structured *one-grammar* representation for uncommon combinations; no two alternate forms for the same meaning.
- Capability-specific field-name schema enumeration and treatment of names that collide with logical operators (e.g. field named `value` or `all`).
- Provenance of a normalized unused `match` on State-free Tests, and whether any optional normalization is worth adopting at all.
- Exact front-end source vs packaged intermediate boundary: standardize one **authoring syntax**, while the compiler may use a fully explicit private IR for deterministic evaluation.

**Assessment:** Stable enough to **start drafting 0.4**; not stable enough for a normative 0.4 freeze until the remaining named decisions and validator gates are settled.
