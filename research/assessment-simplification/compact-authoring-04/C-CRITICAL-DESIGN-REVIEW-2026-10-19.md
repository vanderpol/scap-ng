# SCAP-NG 0.4-C critical design review: simplicity without semantic erasure

**19 October 2026 · research #245 · first human review packet, NOT normative.**  
Compare with [0.4-A design](../../../../schema/v0.4.0/assessment-language.schema.json), [A source examples and C proof](C-AUTHORING-SAMPLE-REVIEW-2026-10-19.md), [C prototype](../../../tools/research_c_require_language.py), [30-test focused CI](https://github.com/vanderpol/scap-ng/actions/runs/39256215911).  
Owner goal: **dramatically simpler than 0.4-A while preserving capability**. Existing A acquisition/typed Items/Variables/evidence are retained as the execution foundation; this is a research **authoring frontend**. The authoring grammar and its implementation have not been accepted.

## Proposed minimal mental model

An auditor has to answer just three independent questions, not think in terms of OVAL internal plumbing:

1. **Where do we get the Items?** \`from\` names one *supported, version-pinned A capability* and its selector/collection arguments. This is not an alternate collector.
2. **What is required of those Items?** \`must\` applies field predicates **on a single Item** and defines how the *population* is checked. **No Items** is part of the result, not a silent pass.
3. **How do independent checks combine?** \`every\`/ \`one_of\`/ \`not\` over named checks use the existing six-state Boolean engine. These are **not** Item quantifiers.

**Basic C candidate: Windows 11 WDigest — exact source-comparison intent**

\`\`\`yaml
from:
  windows.registry:
    hive: local_machine
    key: 'SYSTEM\CurrentControlSet\Control\SecurityProviders\Wdigest'
    name: UseLogonCredential
must:
  every_item:
    type: dword
    value: 0
\`\`\`

The two simple conditions apply **to the same Registry Item**. \`every_item\` explicitly means **at least one exists, and every selected Item matches**; the scalar fields have their expected-value presence and comparison requirements. That is a compile-time mapping to \`at_least_one_exists_and_all_match\`, *not* the English meaning of vacuous universal truth. For \`type\` and \`value\` the compiler resolves supported fields/types from the **existing A Registry capability mapping**, including DWORD/integer consistency; it refuses \`value: '0'\` when \`type: dword\`. The original converted source Registry view remains unresolved; do not silently choose 64-bit.

**Basic C candidate: Linux /home nosuid (source-exact)**

\`\`\`yaml
from:
  linux.partition:
    mount_point: {matches_regex: '.*\/home'}
must:
  every_item:
    mount_options: {contains: nosuid}
\`\`\`

\`mount_options.contains\` here maps to **at least one observed field value equals "nosuid"**. This does not mean substring containment. The exact source regex is retained; replacing it with \`/home\` exact equality would change the assessed population. This test compiles to the same source-backed 0.4-A selector, State field requirement and Test item requirement; metadata such as \`object_title\` is not generated by this limited Test-piece compiler.

**Default shorthand (proposed only):**

\`\`\`yaml
from:
  windows.registry: {hive: local_machine, key: 'SYSTEM\CurrentControlSet\Control\SecurityProviders\Wdigest', name: UseLogonCredential}
must:
  type: dword
  value: 0
\`\`\`

Bare \`must\` means **one or more Items exist and at least one Item satisfies every listed predicate** (\`at_least_one_exists_and_some_match\`). NOT exactly one Item, NOT every Item. This is intentionally different from the original WDigest all-match source. **Question for human review:** Is a five-character word worth hiding this scope? The compiler tests it, but no owner acceptance of the exact spelling/implicit meaning is claimed. An even safer option is requiring \`must: {any_item: ...}\` and omitting bare \`must\` entirely if first-read reviewers misinterpret it.

## A misleading simplification and its counterexample

Two collected Registry Items:

| Item | Storage type | Value | Conforms? |
| --- | --- | --- | --- |
| first | DWORD | 0 | Yes |
| second | DWORD | 1 | No |

**Bare \`must\`: Pass** (at least one matches). **\`must.every_item\`: Fail** (not all match). If no Items are collected successfully, both fail. If collection is incomplete with only a good Item, \`every_item\` remains Unknown while bare \`must\` may already be decisively True. This is an existing OVAL 5.12.3 Test semantics distinction, not a per-capability exception. The generic C adapter uses the same tested A/OVAL existence and six-state result tables.

## Existence must be expressible, not hand-waved

| Desired common behavior | C candidate | Exact A \`require\` token |
| --- | --- | --- |
| At least one Item exists and one matches all fields | bare \`must: {field: value}\`, or explicit \`any_item\` | \`at_least_one_exists_and_some_match\` |
| At least one exists and every Item matches all fields | \`must: {every_item: {field: value}}\` | \`at_least_one_exists_and_all_match\` |
| At least one exists and exactly one Item matches | \`one_matching_item\` | \`at_least_one_exists_and_only_one_matches\` |
| At least one exists, none match | \`no_matching_item\` | \`at_least_one_exists_and_none_match\` |
| Exactly one Item exists and complies | \`exactly_one_item\` **research only, semantic table proof pending** | \`only_one_exists_and_matches\` |
| Only presence matters | \`must: present\` | \`at_least_one_exists\` |
| Required absence | \`must: absent\` | \`none_exist\` |
| Uncommon or contradictory combined requirements | \`must: {items_exist: ..., items_match: ..., fields: ...}\` or \`special_source_requirement\` | All 20 A paired tokens structurally representable |

The exact A schema has **20** paired tokens and **5** presence-only tokens. The focused test enumerates and recompiles all of them. **Structural expressibility is not runtime semantic equivalence** for every token: notably \`none_exist\` with States, \`only_one_exists_and_matches\`, \`all_exist\` and optional/zero-Item cases require independent execution and source oracle checks. No special token is quietly rewritten to a “closest” common case.

## Adversarial decision ledger

| Design question / tempting shortcut | Decision for research gate | Reason and test |
| --- | --- | --- |
| Let missing evidence count as zero Items | **Reject** | Successful empty: Fail for existence requirement; incomplete/not-collected: Unknown; error: Error; not applicable remains distinct. Existing C cross-capability tests |
| Plain \`must\` means every Item | **Reject** for this candidate | Original shorthand proposal says some Item matches; \`every_item\` is explicit. Multiple-Item regression |
| Exactly one *matching* equals exactly one *existing* | **Reject** | One of two Items may match; distinct A tokens. Adversarial two-Item regression |
| Allow type and value to be satisfied by different Registry Items | **Reject** | Both predicates on same Item; typed WDigest fixtures |
| Treat DWORD \`0\` and string \`'0'\` as the same | **Reject** | Silent coercion alters original source. Strict native field/type validation |
| Automatically choose 64-bit Registry view | **Reject** | Original OVAL view parity unresolved; adapter advertises unverified source view |
| Use \`where: equals /home\` instead of source regex | **Reject** for source conversion | Changes selected Item population. Existing Linux negative fixture |
| Invent field existence defaults without type contract | **Reject** | Native mapping required and only bounded scalar/specific multi-valued fields currently supported |
| Silently accept duplicate YAML keys / extra documents | **Reject** | Parser raises; never “last definition wins” |
| Flatten record members across different parent records | **Reject** | Existing six-state/record counterexample; C complex design must retain a \`same_record\` scope |
| Convert per-parent/foreach requirements into global AND or union | **Reject** | A source RHEL9 counterexample demonstrates materially different results; source correlation retained |
| Make every new authored rule show OVAL existence machinery | **Reject** as language goal | Keep common well-tested combinations short; expose advanced combinations when required |
| Hide rare A operations that cannot be rewritten | **Reject** | Fail closed or compile a source-preserving compatibility IR; not an alternate exposed language |

## Proof completed as of this packet

- A capability-neutral **C requirement-to-A Test-piece adapter** validates selectors/typed predicates against the pinned A supported capability mappings and converts concise \`must\` cases into A's existing Test/State/require language. Source-identical Linux Test semantics and Windows WDigest type+value shape are independently checked.
- A strict YAML loader detects duplicate keys and multiple documents before the authoring compiler runs.
- A prior 16-test C gate exercised common six-state Boolean composition (all 6×6 pairs per operator, plus nested cases), universal complete/empty/incomplete/error/not collected and Registry same-Item fixture behavior. The prior Apache complex DAG reconstruction and genuinely fused two-step value pipeline remain in #245.
- The [C 30-test focused gate](https://github.com/vanderpol/scap-ng/actions/runs/39256215911) includes **structural roundtrip for all 20 paired and 5 presence A tokens**, common named shorthands, positive/negative real Linux and Windows authoring samples, no-coercion/unknown-fields/duplicate inputs, and source semantic counterexamples. These are test *functions*, not the exhaustive number of individual value rows inside each function.

## What is NOT proven / what makes or breaks C

- There is **no production A or C scanner**, no fully source-equivalent 6-STIG C conversion, no independently executed original-OVAL Test+Variable+Item oracle, and no general Registry/WMI/Shell collector parity.
- The C authoring compiler is **not** a complete general-purpose language: it accepts one explicitly supported capability per requirement and subset of fields, no arbitrary nested State/record comparison, source Variables, parallel Test composition or advanced source selectors in its current prototype. Other C research components verify some of those boundaries independently, not as one end-to-end compiler.
- A **drastically shorter** C syntax for the full real 19-Variable Apache Assessment has **not** yet been validated as faithful. Reorganizing 19 operations into pretty labels is not a reduction in conceptual complexity. Source-preserving *operation fusions* and no hidden collection providers must be further demonstrated.
- A first-read novice auditor review is mandatory before accepting bare \`must\`; reviewer confusion about existence disqualifies the shorthand.

**Recommendation (not owner-approved):** Retain C as the leading experimental frontend architecture, but withhold “as capable as A” status until its complete source corpus lowering and runtime semantic gates are satisfied. Prefer **explicit \`every_item\`** whenever all collected Items are required; consider removing bare \`must\` if its scope remains ambiguous to reviewers. Continue the source-compatible A backend and do not build new OS acquisition providers.
