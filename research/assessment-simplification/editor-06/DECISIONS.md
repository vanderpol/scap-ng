# Editor/recipe candidates, version 1

Unpublished experimental yes/no questions. No owner adoption or Board ratification
is inferred from this brainstorming. Prior HC/FR decisions remain unchanged.
Promoting a candidate requires the sole `review/current/` navigation and separate
immutable versioned yes/no GitHub Discussions, 👍 Yes / 👎 No, following existing
eligibility/quorum/disposition conventions. No such promotion occurred here.

| Candidate | Single proposition | Research recommendation |
| --- | --- | --- |
| ER-RD-001 v1 | SHOULD an open shared authoring core expose native document editing/diagnostics independently of frontend? | Yes to a bounded core/one-UI experiment. |
| ER-RD-002 v1 | SHOULD recipes remain optional authoring aids whose output is independently usable native content? | Yes; no scanner catalog dependency. |
| ER-RD-003 v1 | SHOULD recipe-generated content support explicit version pinning, reviewable regeneration and detachment? | Yes; preserves repairability without claiming bugs disappear. |

Tooling decisions still open: library language/process boundary, reference frontend,
recipe metadata/author-time binding format, licensing, catalog ownership and
distribution, UI plugin contract, exact preservation/edit model and validation
fixtures. These are implementation/ecosystem choices, not automatically standards
votes. Recipe runtime semantics, novel operators/provider contracts and capability
support would require separate standards decisions where applicable.

Recommendation is exploratory, not permission to weaken native scope/result
semantics or embed recipe provenance in scanner-facing Assessments. No unresolved
choice blocks saving this brainstorming or conducting a bounded author trial.
