## Questions requiring OVAL Board/design disposition before standardization

- Are scoped principal identity and user-profile/hive collection contracts already
  sufficient across existing supported Objects, or is a new capability needed?
- Can relationship/sequence/table conveniences be entirely optional tooling over
  the existing spec? What independent conformance/source-map obligations apply?
- If a directly evaluated security-property operation is introduced, what defines
  its product versions, complete domain, result/error propagation and mandatory
  scanner support? The earlier restricted audit model is insufficient.
- How should a source manual requirement/automated graph discrepancy be handled
  in migration versus a separately authored improved method? A source repair SHALL
  NOT be hidden in an “equivalent” compiler transform.

Source wording questions (13/12 crypto resources, zero SSH intervals, user-profile
population, exact versus stronger LDAP settings) additionally need publisher/vendor
clarification; they are not automatically OVAL Board language defects. No unresolved
choice blocks this research checkpoint or independent follow-up experiments.

Rejected approaches: one global missing-value default; Windows rights modeled as
POSIX numeric modes; lexical paths instead of resource identity; arbitrary natural
language runtime interpretation; commands/Test selection through Organizational
Input; shell filesystem discovery of any scope; favorable cross-record matches;
registry-only proof of runtime behavior; forced automatic approvals; silent source
repair; dropping a supported feature because this corpus does not use it.
