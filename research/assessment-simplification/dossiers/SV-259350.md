### Original Check Text

Exact XML serialization and complete selectors/links are retained in [source-rule.xml](../evidence/ms_windows_server_dns/SV-259350/source-rule.xml). Text below is the inherited generated procedure, with presentation whitespace normalized:

> Note: This check is not applicable for Windows DNS Servers that host only Active Directory-integrated zones or for Windows DNS Servers on a classified network. Log on to the DNS server using the Domain Admin or Enterprise Admin account or Local Administrator account. Press the Windows key + R and execute "dnsmgmt.msc". On the opened DNS Manager snap-in from the left pane, expand the server name for the DNS server and then expand "Forward Lookup Zones". From the expanded list, click to select each zone. Review the RRs for each zone and verify all of the DNSSEC record types are included for the zone. Note: The DS (Delegation Signer) record should also exist but the requirement for it is validated under WDNS-22-000054. RRSIG (Resource Read Signature) DNSKEY (Public Key) NSEC3 (Next Secure 3) If the zone does not show all the DNSSEC record types, this is a finding.

## Complete baseline dependency explanation

Six Tests OR caching-only, all-forward-zones-AD-integrated, or signed+three positive record-count predicates. Seven shell Objects and four Variables discover/filter zones and invoke per-zone queries. Six States compare output; no external Variables or Sets. General config commands exclude Forwarder/TrustAnchors/autocreated zones; reverse zones are excluded from forward checks.

### Necessary semantics versus representation overhead

The Assessment title references RRSet authorization but body tests relevant DNSSEC presence; title mismatch alone is not a logic defect. Zone identity is lost in stdout counts. Original variable instances may still preserve per-command scope: do not assert cross-zone false pass without an evaluator. Classified input/applicability is not modeled by an external Variable in this graph.

Object status/completeness, Item and entity existence, item/state/variable quantifiers, Boolean nesting and acquisition scope are necessary semantics. Source comment/title, separate serialization wrappers and repeated command/regex construction are not independent security requirements. Named shared Objects and Variables SHALL remain referenceable.

## Methods investigated

A: a fixed structured per-zone administrative query with zone ID and each required RR count/status. B: native DNS record collector with the same typed records. Require per-zone completeness, not independent favorable arrays. Classification is a constrained applicability value in a separate Assessment, never command data.

[Complete after sketch](../proposals/dns-record-completeness.proposal.yaml) — all invented fields use the [experimental contract](../FEATURES.md). This sketch shows the proposed method, not a deployable lossless conversion; applicability/bindings remain unchanged unless separately reviewed. A no-change baseline remains valid.

## Cases and falsification

Three zones each providing a different RR type; one zone query fails; unsigned zone; all AD-integrated; mixed integrated/file zones; caching-only; classified; NSEC rather than NSEC3; record-count zero; stale partial inventory. Preserve source integrated bypass separately from stronger mixed-zone policy.

Executed cases are in [test_semantics.py](../experiments/test_semantics.py) and [results](../evidence/test-results.txt). Additional acquisition/OS cases above are specified, not executed. Per-record missing/error/unknown/multiple-match/partial-collection fixtures are synthetic language experiments, not evidence that source collectors behave that way.
