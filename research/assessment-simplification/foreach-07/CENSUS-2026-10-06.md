## What the direct projection candidates cover

The direct candidates are not one repeated special case. They include:

- account/password Item `home_dir` -> File/TextFileContent path;
- Shadow Item `username` -> Password username;
- TextFileContent captured `subexpression` -> File filepath;
- TextFileContent captured `subexpression` -> Partition mount point;
- TextFileContent captured `subexpression` -> Password username;
- TextFileContent captured `subexpression` -> SELinux security-context path;
- File Item path/filepath -> TextFileContent path/filepath.

Several projected Variables fan out to more than one target Object, so
modernization cannot assume every projected Variable can simply be inlined and
discarded.

Several source Objects also contain Sets and Filters. A foreach representation
must bind the Item population *after* the existing source Object selection,
Set, and Filter semantics; it must not recreate those predicates with subtly
different ordering.

## Aggregation semantics observed

The target Tests in this small census already exercise materially different
existence contracts, including:

- `any_exist`;
- `at_least_one_exists`;
- `all_exist`;
- `none_exist`.

Target Test `check` values include `all` and `at least one`, and target
Object variable selectors include both effective `all` and
`at least one` `var_check`.

This is direct production evidence for the collection-vs-evaluation distinction:
a foreach modernization must preserve the original Object population and each
aggregation layer rather than replacing them with a generic "all iterations
must pass" rule.

## Representative direct patterns

### Account homes -> files

RHEL and Solaris both contain:

```
Password Object
  -> object_component(home_dir)
  -> local Variable
  -> File Object path var_ref
  -> File Test
```

This is the strongest first equivalence class because it appears independently
across platforms and naturally reads as collection expansion.

### Configuration capture -> resource selector

RHEL contains several forms such as:

```
TextFileContent Object
  -> object_component(subexpression)
  -> local Variable
  -> File / Partition / Password / SELinux Object selector
  -> Test
```

This suggests foreach modernization can improve more than filesystem-user
loops. It can express a general typed "collect parent Items, project a field,
use it to collect child Items" relationship.

### Resource -> content chaining

RHEL also contains:

```
File Object
  -> object_component(path or filepath)
  -> local Variable
  -> TextFileContent Object selector
```

This is another useful candidate because the dependency is naturally readable
as child acquisition scoped from a collected parent resource.

## Important complications already visible

1. **Fan-out:** one projected Variable may feed multiple target Objects.
2. **Set/Filter sources:** iteration starts from the selected source Item
   population, not the raw collector population.
3. **Existence diversity:** `none_exist`, `any_exist`, `all_exist`, and
   ordinary at-least-one semantics all occur.
4. **Shared aggregation:** target Items are evaluated under existing Test
   semantics; per-binding verdicts must not be invented.
5. **Helper targets:** some target Objects are intermediate dependencies and are
   not directly referenced by a Test in the same component. The analyzer records
   them, but they should not be the first automatic rewrite class.

## Current conclusion

The production census supports continuing the foreach design.

The best first candidate is a **collection-expansion foreach** over a complete
source Item, with field references such as `user.home_dir`, desugaring to the
same dependency graph and combined target Object population as the faithful
OVAL conversion.

The evidence does **not** yet justify:

- enabling automatic rewrites;
- treating evaluation iteration as equivalent;
- modernizing function-derived Variables generally;
- correlating independent multi-valued sources;
- changing Test/Object/State/Variable result aggregation.

## Next proof step

Build the first executable equivalence fixture family around direct collection
expansion and vary:

- zero/one/many source Items;
- duplicate projected values;
- source filtered/unfiltered Items;
- target zero/one/many Items per binding;
- one binding producing a collection error;
- `any_exist`, `at_least_one_exists`, `all_exist`, and `none_exist`;
- Test `all` and `at least one`;
- target selector `var_check=all` and `at least one`.

Only after those fixtures agree should this candidate family be considered for
promotion from `review_required` toward `safe_automatic`.


## Selector-quantifier refinement

Subsequent analysis split the original 15 direct projections by the OVAL
Object entity's `var_check` semantics:

- **10** use `at least one` for every target selector and are the first
  collection-expansion equivalence family;
- **4** RHEL projections use `all` and therefore require the actual candidate
  entity to compare successfully against every projected Variable value;
- **1** RHEL projected Variable fans out to targets with mixed selector
  quantification.

The focused proof in `tests/test_foreach_selector_equivalence.py` establishes
the first selector-level boundary for equality comparisons: `at least one`
matches the union of per-value selector results, while `all` does not. The
`all` and mixed families SHALL NOT be lowered using the same union rewrite.

This is still only the selector-level proof. Promotion to `safe_automatic`
also requires preservation of collection flags/status, zero-value Variable
behavior, datatype/operation semantics, Test existence/check aggregation, and
decisive evidence.
