# SCAP-NG 0.4.1 Result GUID correlation for enterprise SIEM

**Status:** normative 0.4.1 Results metadata design, not a scanner-runtime qualification. Source of truth: [scan-result.schema.json](../../schema/scan-result.schema.json). One active 0.4.1 schema family in `schema/`; historical 0.4.0 is only in Git history.

## Identity contracts

| Field | Location | Ownership and lifetime |
| --- | --- | --- |
| `machine_guid` | `scan_result.targets[].machine_guid` | Stable **target machine** identity, preferably from trusted enterprise asset inventory or a canonical native machine identifier. One scan may contain multiple different target machines. Does not change for a new scan on the same machine. |
| `app_guid` | `scan_result.scanner.app_guid` | Stable **scanner or agent installation/application** identity. Separate from the scanner's software version, target machine, current process, scan session and content. |
| `scan_session_guid` | `scan_result.scan_session_guid` | Fresh UUID **once per scanning session**, reused in all correlation events and result views for that session. Changes on a new scan session. Distinct from `run_id`, whose existing meaning and representation are retained. |

All three use **lowercase 8-4-4-4-12 hyphenated UUID** syntax. `format: uuid` plus explicit `pattern` enforces lexical canonicalization when JSON Schema format-checking is not enabled. UUIDs are correlation metadata only: they are neither evidence, signatures, source-result proofs nor authorization tokens.

All three fields are **optional in the initial 0.4.1 schema** to preserve result validation for scanners not yet integrated with enterprise identity providers. A scanner that knows the identifiers must emit them consistently; unknown/untrusted identity must be omitted, **never invented** from hostnames, MAC addresses or arbitrary all-zero GUIDs. A random session UUID is appropriate because session identity is intentionally ephemeral; a random *machine* UUID generated each scan is inappropriate.

The scanner owns `app_guid`; an authorized target/asset provider owns each `machine_guid`. Cross-tenant machine GUID reuse and enterprise inventory identity should be governed by the deployment's privacy and identity policy. Do not assume a single machine per scan; the field is intentionally placed within each target record, not at scan root.

## Example

See [scan-siem-correlation.json](../../examples/results/scan-siem-correlation.json).

```json
{
  "scan_result": {
    "result_schema_version": "0.4.1",
    "run_id": "run-2026-11-13T23:59:00Z-001",
    "scan_session_guid": "9c9e47d5-e862-4e3b-9d63-76d54c92eb2e",
    "started_at": "2026-11-13T23:59:00Z",
    "scanner": {
      "app_guid": "661c9d32-2baf-4f15-a4a9-9686adbd6008"
    },
    "targets": [{
      "id": "target-001",
      "machine_guid": "0f921bc7-150f-4bfa-9618-9eb7cfad22b2"
    }],
    "benchmark_results": [{
      "benchmark_result_ref": "benchmark-001.json",
      "benchmark_id": "rhel9-example",
      "target_ref": "target-001"
    }]
  }
}
```

## Emitter, package and event contract

The Scan Result is the source of identity truth. A Result-package reader or SIEM event adapter may project these fields onto each emitted event, but **must reuse the same values**, not assign new GUIDs to each Rule, Assessment or evidence Item. The existing `benchmark_results[].target_ref` binds an event to the appropriate per-target `machine_guid`. The existing `run_id` continues to link Result package manifest, scan and Benchmark Results.

On retries or resume, preserve the session identifier only when resuming the **same** scan session with the same context. A new independent scan gets a new session identifier even on the same host. Redact or suppress stable machine/app identifiers when the organization’s SIEM disclosure policy requires it; do not silently replace with fabricated values.

**Tests and release gates:** [test_result_correlation_guids.py](../../tests/test_result_correlation_guids.py) validates a real complete 0.4.1 example and rejects upper-case, malformed and scan-root machine GUIDs. Runtime emitter requirements are tracked in [RI #67](https://github.com/vanderpol/scap-ng-ri/issues/67); downstream canonical schema-change gates remain [Tools #59](https://github.com/vanderpol/scap-ng-tools/issues/59), [VS Code #65](https://github.com/vanderpol/scap-ng-vscode/issues/65), and [RI #66](https://github.com/vanderpol/scap-ng-ri/issues/66). No current RI emitter or SIEM integration is claimed qualified by the schema change alone.
