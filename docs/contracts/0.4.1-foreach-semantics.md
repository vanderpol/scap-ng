# Native `for_each` semantic packet — SCAP-NG 0.4.1

This packet accompanies the compact Object-level `for_each` syntax in PR
#130. It is deliberately separate from JSON Schema: a schema can check the
shape of `item`, `in`, `reduce`, and `from`, but it cannot resolve a source
Object, type an Item field, preserve a missing dependent collection, or prove
that a reducer did not turn incomplete evidence into PASS.

The packet is a **proposed executable contract pending owner approval under
canonical Issue #76**. It is not a claim that RI, Tools, or Studio implements
this feature. The source-independent vectors live in
`conformance/0.4/foreach/semantic-vectors.json`; the schema-valid witness is
`conformance/cases/core/foreach-semantic-vectors.assessment.yaml` and its
separate expected manifest.

## 1. Iteration model and the missing-Item invariant

Expansion is a bounded stream, not a flattened dependent population. For each
source Item `s`, the evaluator creates exactly one iteration record before
reduction:

```text
iteration {
  source_item_ref       // stable source Item identity and ordinal
  bindings              // alias -> typed scalar field binding
  dependent_status      // complete, empty, denied, error, cancelled, partial
  dependent_item_refs   // possibly an empty list; never omitted
  require_outcome       // true, false, unknown, error, not_evaluated,
                        // or not_applicable
  evidence_complete
}
```

A dependent collection with zero Items is therefore not equivalent to “no
iteration”. If the per-iteration Require says `items_found: one_or_more`, a
complete zero-Item dependent collection produces `false` for that iteration.
If acquisition is denied, errored, cancelled, or partial, it produces the
corresponding non-Boolean status and an incomplete iteration. A reducer MUST
consume that record. It MUST NOT delete it while flattening the remaining
Items.

Consequently, a source with two Items where one dependent lookup is empty and
the other passes reduces as `false` under `every`; it cannot become PASS by
aggregating only the one returned dependent Item. The independent mutation
vector `missing-dependent-cannot-disappear` proves this invariant.

## 2. Reduction contract

`reduce` is required. It reduces **per-source-Item Require outcomes**, never
raw dependent Items. Status precedence is applied only after decisive Boolean
conditions have been considered. A definitive failure (for example one failed
iteration under `every`) remains definitive even if later collection is
cancelled; it does not imply population completeness.

The following tables use `T`, `F`, `U`, `E`, `N` for TRUE, FALSE, UNKNOWN,
ERROR, and NOT_EVALUATED. `C` means the source population is complete and `P`
means it is partial/unknown. “Empty” means complete with zero source Items.

### `every`

| Source/iterations | Outcome | Reason |
|---|---|---|
| Empty | `UNKNOWN` | No iteration exists; `every` is not implicit vacuous PASS. |
| Complete, all `T` | `TRUE` | Every source Item has a passing Require. |
| Complete, any `F` | `FALSE` | One failed iteration is decisive. |
| Complete, no `F`, any `E` | `ERROR` | An unresolved acquisition error prevents a complete all-pass claim. |
| Complete, no `F/E`, any `U` | `UNKNOWN` | A pending iteration may change the result. |
| Complete, no `F/E/U`, any `N` | `NOT_EVALUATED` | The population is known but a branch was not evaluated. |
| Partial, any `F` | `FALSE` | The observed failure cannot be reversed by unseen Items. |
| Partial, otherwise | `UNKNOWN` | Unseen source/dependent evidence can change all-pass status. |
| Cancelled, prior `F` | `FALSE` | Decisive failure precedes cancellation. |
| Cancelled, otherwise | `NOT_EVALUATED` | Cancellation prevents a complete reduction. |

### `one_or_more`

| Source/iterations | Outcome | Reason |
|---|---|---|
| Empty | `FALSE` | No source Item passed. |
| Complete, any `T` | `TRUE` | One passing iteration is sufficient. |
| Complete, no `T`, any `E` | `ERROR` | No passing iteration is established and an error is unresolved. |
| Complete, no `T/E`, any `U` | `UNKNOWN` | An unknown iteration may pass. |
| Complete, no `T/E/U`, any `N` | `NOT_EVALUATED` | No passing iteration was evaluated to completion. |
| Complete, all `F` | `FALSE` | The complete population has no passing iteration. |
| Partial, any `T` | `TRUE` | At least one pass is mathematically decisive. |
| Partial, otherwise | `UNKNOWN` | Unseen Items may contain the first pass. |
| Cancelled, prior `T` | `TRUE` | Decisive pass precedes cancellation. |
| Cancelled, otherwise | `NOT_EVALUATED` | No passing iteration was observed before cancellation. |

### `exactly_one`

| Source/iterations | Outcome | Reason |
|---|---|---|
| Empty | `FALSE` | Zero passing iterations is not exactly one. |
| Complete, at least two `T` | `FALSE` | Too many passing iterations is decisive. |
| Complete, one `T`, remaining `F` | `TRUE` | Exactly one complete passing iteration exists. |
| Complete, zero `T`, all `F` | `FALSE` | No passing iteration exists. |
| Complete, one `T`, any `E/U/N` | corresponding status | The second-pass count is unresolved. |
| Partial, at least two `T` | `FALSE` | Too many passes are decisive. |
| Partial, otherwise | `UNKNOWN` | A missing Item can add or remove the unique pass. |
| Cancelled, at least two `T` | `FALSE` | Too many passes were observed. |
| Cancelled, otherwise | `NOT_EVALUATED` | Unseen iterations prevent an exact count. |

### `none`

| Source/iterations | Outcome | Reason |
|---|---|---|
| Empty | `TRUE` | No iteration passed; the empty population is explicit. |
| Complete, any `T` | `FALSE` | A passing iteration violates `none`. |
| Complete, no `T`, any `E` | `ERROR` | No-pass status cannot be established around an error. |
| Complete, no `T/E`, any `U` | `UNKNOWN` | An unknown iteration may pass. |
| Complete, no `T/E/U`, any `N` | `NOT_EVALUATED` | The no-pass claim is not fully evaluated. |
| Complete, all `F` | `TRUE` | No iteration passed. |
| Partial, any `T` | `FALSE` | A passing iteration is decisive. |
| Partial, otherwise | `UNKNOWN` | Unseen Items may pass. |
| Cancelled, prior `T` | `FALSE` | Decisive violation precedes cancellation. |
| Cancelled, otherwise | `NOT_EVALUATED` | No-pass status is incomplete. |

A source-level `NOT_APPLICABLE` is not an iteration and bypasses expansion. A
source-level `ERROR`, denied authority, or invalid binding is propagated as
`ERROR` (or an explicit authoring failure) rather than treated as an empty
source. These distinctions are retained in the Result lineage.

## 3. Source, duplicate, dependency, and cancellation rules

* Empty source, complete source with zero dependent matches, and failed source
  acquisition are three different states.
* Source identity is `(Object reference, Item identity, source ordinal)`. Equal
  field values do not authorize deduplication. Duplicate source identities are
  preserved as separate iteration records and are a source-population warning
  unless the source capability explicitly defines identity uniqueness.
* A missing dependent Item is evidence in the iteration record. It is subject
  to the dependent Test's Item/field cardinality and participates in reduction.
* A source or dependent `ERROR` is not rewritten as `FALSE`; permission denial,
  unsupported acquisition, malformed data, and system errors retain their
  status and diagnostic provenance.
* Cancellation propagates to source and dependent collectors. A decisive
  Boolean found before cancellation may remain the Test outcome, but
  `evidence_complete` remains false and the Result says `cancelled`.
* Resource limits, cycle detection, and maximum expansion depth are
  acquisition/evaluation statuses, not empty populations.

## 4. Lexical bindings, chaining, and types

`item` introduces one alias in the dependent Object's lexical scope. A
`from: alias.field` selector is valid only when:

1. `alias` is the current `for_each.item` or an inherited alias from an
   enclosing expansion;
2. `field` is a scalar field declared by the source capability's Item contract;
3. the field datatype and cardinality are exactly compatible with the target
   selector (no stringification, numeric widening, or singleton coercion); and
4. the target capability has a reviewed selector position admitting bindings.

Unknown aliases, unknown fields, multi-valued fields where a scalar is
required, incompatible datatypes, and bindings on an unreviewed/parameter-only
capability are rejected before collection. JSON Schema can check the lexical
shape but not these source-dependent conditions; the compiler must enforce
all four.

Chaining is lexical inheritance: a child sees its own alias plus all visible
ancestor aliases, with each binding retaining its source iteration lineage.
Alias shadowing is rejected rather than silently rebinding an ancestor. A
source-reference graph containing a cycle is a compile error before any
collector starts. A child cannot reference an alias from a sibling or a
completed unrelated Object. Expansion has explicit depth, Item, byte, time,
and concurrency limits; it is never an implicit Cartesian product.

The all-capability audit covers all 101 supported mappings, not merely the 15
currently reviewed selector overlays: 15 reviewed capabilities (28 selector
fields), 62 selector-bearing but unreviewed capabilities, and 24 capabilities
without selectors. Only the first group is admitted by the generated closed
selector overlay. The other groups remain explicit compiler/source-conformance
holds and cannot claim `for_each` selector support.

## 5. Correlated selector transformations

Existing 0.4.1 Variable functions (`concat`, `unique`, `merge`, `count`, and
other functions in `variable-expression.schema.json`) are Assessment-scoped.
They can transform a known Variable population, but they cannot safely read a
per-iteration alias. Therefore this is **not** currently valid native syntax:

```yaml
# intentionally withheld: no implicit alias-to-Variable capture
filepath: {from: concat(user.home_dir, literal: /.ssh/authorized_keys)}
```

The desired `home_dir + "/.ssh/authorized_keys"` operation needs an approved
correlated expression contract defining evaluation scope, scalar/list output,
status propagation, escaping, and selector typing. Until that decision, a
converter must use an existing source-traced Object/Variable lowering or hold
the case; it must not invent a new `from` expression or stringify values.

## 6. Result lineage and zero-item iterations

A canonical Result extension or approved result-side representation must retain
at least:

* source Object identity and source Item identity/ordinal;
* alias name and typed binding provenance (redacted value where requested);
* dependent Object identity and dependent collection status;
* dependent Item references, including an explicit empty list;
* per-iteration Require outcome, decisive reason, evidence completeness,
  cancellation and resource-limit status; and
* the reducer, ordered iteration count, reducer outcome and completeness.

This makes a zero-Item dependent iteration distinguishable from an omitted
iteration. Raw secrets and sensitive fields remain governed by existing
`redact_result`; lineage is not permission to emit them.

## 7. Conditional branches

A conditional expression evaluates conditions in order. A true branch evaluates
only its `then` expression; later branches are suppressed. An absent Input
(`input_provided`) selects the explicit `else`; an indeterminate condition
propagates `UNKNOWN` and does not fall through to `else_if`/`else`. Suppressed
branches must not collect source or dependent Items, and Results identify them
as `not_evaluated` due to branch suppression, not as empty evidence.

## 8. Normative decisions requested under Issue #76

The following are now explicit rather than hidden implementation assumptions:

1. Approve or change the four reducer tables, especially empty-source `every`
   (`UNKNOWN`) and empty-source `none` (`TRUE`).
2. Approve duplicate identity preservation and the rejection of alias shadowing.
3. Approve exact typed scalar binding with no implicit casts.
4. Decide whether correlated transformations are added to 0.4.1 or deferred to
   0.5.0, and their exact expression grammar.
5. Decide the canonical Result placement for iteration lineage and incomplete
   zero-item records.
6. Approve the all-capability policy: only reviewed selector contracts are
   executable; unresolved/parameter-only capabilities reject bindings before
   collection.

Until these decisions are approved, PR #130 remains open and the syntax is a
review candidate, not a frozen executable contract. RI/Tools/Studio support
must not be claimed from schema validation or these proposal fixtures alone.
