# `for_each` architectural recommendation (SCAP-NG 0.4.1)

**Decision status: MODIFY / DEFER ADOPTION.** Keep PR #130 open for owner
approval under canonical Issue #76. `for_each` should remain a candidate native
feature, but no existing Object-derived Variable, Set, Filter, or evaluator
mechanism should be removed yet. The current evidence shows a real semantic
capability—correlated per-source-Item evaluation—but does not show a lossless
replacement for the existing language.

This recommendation is based on the source-pinned 65-benchmark audit in
[`foreach-consolidation-65.json`](evidence/foreach-consolidation-65.json), the
semantic packet in [`0.4.1-foreach-semantics.md`](0.4.1-foreach-semantics.md),
and the source-backed examples in [`0.4.1-foreach-source-examples.md`](0.4.1-foreach-source-examples.md).
It is a design review, not a claim that RI, Tools, or Studio implements the
feature.

## 1. What is genuinely new

An Object-derived Variable produces an ordered value population. It does not,
by itself, express that a dependent acquisition and Require evaluation must be
performed once for **each source Item**, with a preserved join key and one
reducible outcome per source Item. Flattening the source field into a Variable
can lose:

* source Item identity and ordinal;
* the distinction between two equal values from different Items;
* a dependent collection that returned zero Items for one source Item;
* per-source UNKNOWN, ERROR, denied, partial, or cancelled status; and
* the evidence needed to explain which source caused a result.

`for_each` is therefore genuinely new when it means:

```text
source Item -> typed binding -> dependent acquisition -> per-source Require
            -> explicit reducer -> lineage-preserving Result
```

It is **not** new when it is used merely to compute a list, deduplicate a list,
combine populations, or pass one already-computed value to another Object.
Those remain the jobs of Variables, functions, Sets, and Filters.

The feature must not create a Cartesian product. One source Item creates one
iteration record; dependent Items do not become source iterations. An explicit
resource limit bounds source population, expansion depth, dependent fan-out,
bytes, time, and concurrency.

## 2. Realistic DISA requirements that benefit

These cases are representative of requirements where a host first discovers a
population and then checks a related object. The IDs are source examples, not
execution proof.

| Rule / product | Correlated requirement | Why a plain Variable is insufficient |
|---|---|---|
| Ubuntu `SV-270827`, `SV-270828`, `SV-270830` | Discover each local account/home and inspect account-specific files or settings. | Equal home paths, duplicate accounts, missing files, and denied homes need independent lineage and population status. |
| RHEL `SV-230399`–`SV-230401` | Discover package/config records and evaluate a dependent package or configuration predicate for each record. | The dependent check must not turn a missing record into an omitted value or globally passing population. |
| NGINX `SV-278388` | Discover configuration records and inspect the corresponding configuration path. | A list of paths loses which discovered record produced each path and which record had an empty dependent result. |
| Windows DNS `SV-259338` | Discover DNS names/records and evaluate a related setting per name. | Windows item identity, case rules, and remote/provider errors must remain attached to each name. |
| Kubernetes `SV-242405`, `SV-242408` | Discover manifest files and apply owner/permission predicates to every manifest. | Recursive/path discovery and per-file permission failures must not be reduced to a flattened string list. |
| RHEL 9 `SV-258166` | Discover package/config data, then perform a source-correlated dependent check with a distinct State predicate. | Shared physical collection is useful, but logical populations and Require outcomes remain per source Item. |

These examples benefit from correlation only if the source Item field is a
reviewed scalar selector with a declared datatype. Cases requiring a
transformation such as `home_dir + "/.ssh/authorized_keys"` still need an
approved scoped-expression contract; `from` must not silently become an
expression language.

## 3. Full-corpus consolidation result

The available source-preserving corpus contains 65 benchmark streams, 8,892
source Rules, 4,524 emitted Assessments, and 4,368 blocked Rules. It is a
historical 0.4.0-era automated subset; the blocked source Rules have not been
reinterpreted as current 0.4.1 executable graphs.

The audit found:

| Construct / pattern | Count | Interpretation |
|---|---:|---|
| Direct `values: {object, field}` Variables | 160 | Object-derived value populations, not all transfer idioms. |
| Selector references from those Variables | 147 | Some Variables feed more than one selector. |
| Sole-transfer Variables | 121 | Only plausible consolidation pool. |
| Selector references from sole-transfer Variables | 145 | Multiple dependent consumers exist. |
| Sole-transfer cases retaining `value_match` | 97 | Cardinality cannot be replaced by scalar `from` without a normative rule. |
| Sole-transfer cases in shared/Set/Filter positions | 24 | Moving correlation changes population/status semantics unless proven. |
| Object-derived Variables used outside selectors | 37 | Legitimate value use; do not retire. |
| Variables used both in selectors and elsewhere | 2 | Shared computation/lineage; do not rewrite automatically. |
| `concat`, `regex_capture`, `merge`, `unique` expressions | 337, 90, 54, 24 | Legitimate computation/aggregation inventory. |
| Normalized duplicate-Test groups | 63 groups / 148 Tests | Syntactic template similarity only. |
| Syntactic Test reduction upper bound | 85 | Not a semantic or YAML reduction claim. |
| Proven lossless `for_each` replacements | **0** | No independent 0.4.1 equivalence receipt exists. |
| Verified Variable/YAML reduction | **0** | Do not manufacture a simplification number. |

The duplicate-Test census removes presentation titles and replaces reference
names only within each Assessment. It identifies repeated shapes, not shared
source Objects, equal acquisition semantics, or interchangeable Results. A
future optimizer may use these groups to propose shared traversal, but it must
not merge their logical populations or provenance automatically.

The theoretical transfer pool is at most 121 declarations and 145 selector
references. That is an upper bound, not a promised reduction. The replacement
would add explicit source Object, `for_each`, reducer, and lineage fields, so
parsed AST nodes and independently verified authoring bytes—not rendered line
counts—must measure complexity.

## 4. What existing mechanisms can and cannot be retired

### Retain

* Variable expressions and functions for computation, conversion, regex
  capture, concatenation, aggregation, counting, deduplication, and source
  fidelity.
* Variables shared by multiple consumers or used in Requirements, Evaluate
  conditions, Set operands, or Filters.
* Set union/intersection/difference and Filter semantics.
* Named/shared Objects as reusable acquisition definitions.
* The existing Test/Require evaluator and explicit status/completeness model.

A Variable is a candidate for eventual authoring normalization only when all of
these are true: it is local; its expression is exactly `values(object, field)`;
it is used only by direct dependent selector positions; the field is a typed
scalar; there is no `value_match`, Set, Filter, or transformation; and a
source-equivalence test proves identical duplicate, empty, order, status,
completeness, and Result behavior.

### Do not retire now

No construct meets that full proof in the current corpus. In particular,
retiring the Variable evaluator would break OVAL 5.12.3 conversion fidelity and
would make source graphs requiring population cardinality or transformations
less explicit, not simpler. If a future campaign proves a narrow subset
redundant, coordinate a versioned deprecation across canonical schema, Tools,
VS Code metadata, and RI, with a source-fidelity escape hatch and a migration
period. This requires owner approval; PR #130 must not perform the removal.

## 5. Correlated Require contract required before adoption

The current `fields` predicates compare observed fields with authored values;
they do not define a reference to the active source alias. A compact syntax
such as `owner_uid: {from: source.uid}` is therefore proposal material, not an
implicit extension of the current grammar.

If canonical Issue #76 admits correlated Require, it should require:

1. **Explicit scope.** Every source-dependent operand names the active alias or
   an approved inherited alias; sibling and out-of-scope aliases are rejected.
2. **Typed operands.** Source field datatype and cardinality exactly match the
   target field/predicate. No stringification, numeric widening, singleton
   coercion, or implicit list flattening.
3. **Per-source evaluation.** The dependent Test is evaluated independently
   for every source Item. Its Require sees only that iteration's dependent
   population and source binding.
4. **Missing dependent evidence.** A complete zero-Item dependent collection is
   an evaluated empty population and participates in Require cardinality. It
   is never omitted from the reducer input.
5. **Status preservation.** Denied, unsupported, ERROR, UNKNOWN, partial, and
   cancelled acquisition statuses remain statuses. They are not rewritten as
   FALSE or as empty success.
6. **Duplicate identity.** Equal field values from distinct source Items are
   distinct iterations unless the source capability explicitly declares an
   identity key and the author explicitly requests deduplication.
7. **No Cartesian expansion.** Chained bindings inherit lexical lineage and
   have bounded depth/fan-out. Alias shadowing and dependency cycles are
   compile errors.
8. **Definitive early termination.** `every` may stop on a decisive FALSE and
   `one_or_more` may stop on a decisive TRUE, but Result completeness must say
   that collection was intentionally truncated.

The reducer tables in the semantic packet define independent empty, missing,
duplicate, incomplete, UNKNOWN, ERROR, and cancellation behavior. They must be
approved as canonical rather than inferred from JSON Schema.

## 6. Variable functions and derived selectors

Assessment-scoped functions can transform a complete Variable population, but
an existing function does not implicitly capture a per-iteration alias. In
particular, `concat`, `regex_capture`, `split`, `substring`, `merge`, `unique`,
and `count` remain legitimate for population computation or aggregation.

For a derived selector such as `home_dir + "/.ssh/authorized_keys"`, there
are two safe choices:

* retain a source-traced Variable/Object lowering until canonical scoped
  expressions define output datatype, escaping, cardinality, status, and
  lineage; or
* add an explicitly approved iteration expression that accepts only typed
  scalar bindings and is evaluated inside the iteration.

Do not overload `from` with arbitrary Variable functions. A converter must hold
or retain the source-fidelity form when the transformation cannot be expressed
without changing semantics.

## 7. Applicability and capability boundary

The all-capability review covers 101 supported mappings: 15 reviewed selector
capabilities with 28 selector fields, 62 selector-bearing capabilities still
unresolved, and 24 capabilities without selectors. The 15 reviewed mappings
are the only executable selector overlay set at this stage. A binding against
one of the 62 unresolved mappings must fail compilation or remain an explicit
hold; it must not be accepted because a generic schema shape happens to fit.

The review includes Windows capabilities and must retain platform-specific
identity, case, provider, registry, WMI, and remote-authority semantics. The
experimental OVAL 6.0-derived mapping set (12 mappings identified in the
external Tools evidence) is outside the qualified OVAL 5.12.3 denominator.
Schema presence is not OVAL 6.0 runtime support. Each OVAL 6.0 mapping needs
its own source, collector, negative, status, and expected-result qualification.

## 8. Result lineage and resource limits

A canonical result needs an iteration record with source Object/Item identity
and ordinal, alias and typed binding provenance (redacted as required),
dependent Object and collection status, an explicit dependent Item reference
list including zero length, per-iteration Require outcome/reason/completeness,
cancellation/limit status, reducer, iteration count, and final reduction.

Suggested implementation limits are policy inputs, not normative defaults:

| Budget | Required behavior at exhaustion |
|---|---|
| source Items / dependent Items | Stop admission, mark incomplete/limited; never treat the remainder as empty. |
| expansion depth / fan-out | Reject or return bounded ERROR before unbounded collection. |
| bytes / temporary storage | Cancel dependent consumers and publish an explicit limit status. |
| wall time / CPU | Propagate cancellation; preserve already decisive Boolean only with incomplete lineage. |
| concurrent collectors / open descriptors | Apply one shared Benchmark budget; queue or hold excess work. |

A definitive Boolean can remain valid when the logic makes it irreversible, but
that is separate from evidence completeness. A complete all-pass claim cannot
be made after a collection limit, cancellation, denied mount, or unseen source
population unless the approved reducer semantics prove it decisive.

## 9. Recommendation and gates

**Recommend: modify and defer broad adoption.** Retain the compact syntax as a
candidate for explicit correlation, but do not claim language simplification,
converter replacement, or runtime support yet.

Before adoption, canonical Issue #76 should approve:

1. all reducer truth tables and source-level status precedence;
2. per-source Require grammar and correlated operand typing;
3. duplicate identity, chaining, shadowing, cycle, and depth rules;
4. derived-selector expression scope and Variable-function interaction;
5. Result lineage location and redaction requirements;
6. reviewed capability selector registry, including Windows policy; and
7. budget/cancellation semantics and definitive-outcome completeness wording.

Then run a bounded equivalence campaign across the 121 transfer candidates,
including the 97 cardinality cases and 24 Set/Filter/shared cases. Compare
original OVAL, current NG, and proposed NG on empty, duplicate, denied, error,
partial, cancellation, and large populations. Only candidates with independent
same-result and same-evidence receipts may be normalized.

Until those gates pass, the correct architectural choice is **retain both
mechanisms without removal**: use `for_each` where explicit correlation and
lineage are genuinely valuable, and use Variables where computation,
aggregation, transformation, shared reuse, or source fidelity is the actual
requirement.
