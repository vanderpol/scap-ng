# SCAP-NG 0.4.1 — complete empty populations

Normative native correction, owner direction 2026-11-27. This supersedes the empty-source and empty-expected Variable holds in the 0.4 evaluation addendum. No new authoring grammar. OVAL 5.12.3 State references to zero-value Variables intentionally differ; conversion must retain provenance and disclose this semantic difference, not add artificial fallback values.

## Population and evidence

A successfully evaluated, authoritative population of zero Items or values is valid complete data. Emptiness alone SHALL NOT cause ERROR or UNKNOWN. A missing/unbound reference, invalid content, unsupported operation, failed acquisition, incomplete evidence or insufficient authority SHALL NOT be converted to successful emptiness. Apply existing status/decisiveness contracts; unresolved combinations remain explicit holds. A legitimate empty string is one string value, never zero values.

Object selection, Set and Filter operations may produce zero Items. Do not fabricate Items. An existing Item may have zero values of an acquired field; encode authoritative field absence using typed status `does_not_exist`, not a physically omitted/unacquired field. Shellcommand successful execution is one Item regardless of output; stdout, stderr and capture cardinalities are independent. A failed or unauthorized command is not evidence of absence; honor the authored exit-status/stderr behaviors and explicit predicates. No new security permission is implied.

Variable extraction of a complete zero-Item collection or explicitly absent selected field produces zero values. Explicit absent fields contribute zero in mixed present/absent populations; preserve source identities and values/duplicates in source order. A missing field without an authoritative absence marker is not sufficient proof. Preserve datatype from canonical field metadata/expression (including typed empty literals), not an invented scalar or consumer-directed cast. Variable result uses existing `status: complete`, `cardinality: zero`, `values: []`; existing `zero_values` must be interpreted as authoritative empty only when acquisition/evaluation evidence establishes that status, never as failure or partial evidence.

## Cardinality

For complete populations, with N members and M successful comparisons, use the existing finite cardinality definitions even for N=0:

| Matching cardinality | N=0, M=0 |
|---|---|
| none | TRUE |
| exactly_one | FALSE |
| one_or_more | FALSE |
| every | TRUE |

The same rule applies at each independent matching layer (`value_match`, `values_matching`, `items_satisfying`). Existence counts are independent: `none` and `zero_or_more` (where admitted) are true on zero; `exactly_one` and `one_or_more` are false. An unsatisfied existence predicate cannot be rescued by vacuous matching. Authors should use explicit positive existence requirements when absence must fail. The universal/none results above are intentional mathematical vacuity, not a waiver of acquisition authority. Do not evaluate an absent expected operand as an empty string, synthetic mismatch, invalid regex, or implicit default. A genuine malformed or unsupported operand still follows its established error/status contract.

Extend Model A: a successfully resolved Variable used as a `variable.value` source is one logical source group with N typed values, including N=0. This is a logical grouping, not a collected Item. `items_found` counts the group; `values_found` counts its values. An unresolved Variable does not create a successful group. Aliases preserve empty status and datatype.

## Functions and Sets

For known complete inputs, `count([])` yields integer 0; alias and `unique([])` yield []; Cartesian `concat` with any empty input yields []; element-wise transformations over empty input yield []; Shellcommand selection with no matching lines/captures yields zero values. Distinguish this from the existing Variable `regex_capture` function: for a nonempty input with no match or no capture group, the current function contract emits an empty string per input. Preserve that function-specific behavior; zero input values still yield zero outputs. A genuine empty capture is a scalar empty string. Union/intersection/difference and filters can legitimately produce zero Items. Invalid expressions, invalid regex, unknown/partial dependencies and undefined mathematical operations are not made successful by emptiness. Function-specific contracts (including merge, time arithmetic and type/cast rules) still govern; audit remaining edge cases separately rather than inventing defaults.
