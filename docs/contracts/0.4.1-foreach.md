# Native `for_each` contract — SCAP-NG 0.4.1

This document records the active 0.4.1 language contract for bounded collection
expansion. The JSON Schema is authoritative for syntax; this document records
runtime obligations that JSON Schema cannot enforce by itself.

## Authoring shape

`for_each` is a property of an inline or named Object:

```yaml
shared_objects:
  users-object:
    object_title: Users
    capability: unix.file
    filepath: {equals: /etc/passwd}

tests:
  dependent-test:
    capability: unix.file
    object:
      for_each: {item: user, in: users-object}
      filepath: {from: user.full_path}
    # require and reported_elements are ordinary Test properties
```

- `for_each.item` is a lexical alias for one source Item.
- `for_each.in` is a reference to one named shared Object in the enclosing
  Assessment. The reference is resolved before collection; an unresolved
  reference is an authoring/compile error, never an empty source.
- A dependent Object may use `{"from": "alias.field"}` for a capability
  selector. The binding is a selector value, not a literal comparison.
- A source Object may itself be expanded. Chained expansion inherits the
  existing aliases and preserves lineage; implementations must not turn it
  into an unbounded or implicit cross-product.
- Existing Objects without `for_each` retain their 0.4.1 meaning unchanged.

The schema admits the common shape and lexical syntax. Compiler validation must
also confirm that the alias is visible, the field exists in the source Item
contract, the bound value has the selector datatype/cardinality, and the
capability accepts the selector in that position.

## Collection and evaluation semantics

Expansion is one source Item in, at most one dependent selector binding per
source Item, and one correlated dependent collection context. It does **not**
combine two independent source Objects. Duplicate source identities are not
silently collapsed: the collector/evaluator reports the duplicate according to
its source-population policy and preserves source lineage.

The following states remain distinct:

- complete empty source population;
- complete source population with zero dependent matches;
- missing, denied, unsupported, error, cancelled or budget-truncated source;
- incomplete source population or incomplete source Item evidence;
- a dependent collection error for one binding.

A complete empty source is an ordinary empty population and is evaluated by the
Test's Item cardinality. An incomplete, denied, errored, cancelled or truncated
source cannot satisfy a complete-population requirement merely because no
correlated Items were emitted. A decisive false remains false only when unseen
source/dependent evidence cannot reverse it. Source and dependent status,
completeness, budget and lineage are retained in Results.

Expansion is bounded by the scanner/session limits for source Items, emitted
Items, bytes, time and downstream concurrency. Cancellation propagates to the
source and all active dependent consumers. A consumer may stop after a
mathematically decisive outcome without implying that collection was complete;
Results must distinguish decisive evaluation from evidence completeness.

## Compatibility and implementation boundary

| Area | 0.4.1 disposition |
| --- | --- |
| Existing non-`for_each` authoring | Unchanged and backward compatible |
| One named source Object | Supported by the grammar; compiler must resolve it |
| Correlated lexical alias | Supported; no implicit Cartesian product |
| Selector binding from `alias.field` | Supported; typed/cardinality checks are runtime/compiler obligations |
| Chained expansion | Admitted; lineage must remain correlated and bounded |
| Literal prefix/suffix or other derived selector values | Not implied by this grammar; require an explicit approved expression and compiler support |
| Missing/multi-valued/invalid source field | Fail closed as an authoring/collection status; never invent a selector |
| Source duplicates and incomplete populations | Preserve and report; never silently convert to a complete empty source |
| Results lineage | RI/Tools must retain source Object, source Item and alias/binding provenance |
| Converter/editor/runtime pins | Must be repinned to this exact canonical schema commit before claiming consumer support |

This language update does not by itself claim Tools conversion, VS Code
editing, RI planner integration, or live scanner equivalence. Those are linked
downstream qualification gates and must use the same schema commit and digest.
