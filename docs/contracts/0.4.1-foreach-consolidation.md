# `for_each` language-consolidation review

This review asks whether native Object-level `for_each` should replace existing
Object-derived Variable and selector-transfer idioms, rather than becoming a
second way to express them. It is an architectural analysis only. No existing
construct is removed, deprecated, or rewritten by this work.

The machine receipt is
[`evidence/foreach-consolidation-65.json`](evidence/foreach-consolidation-65.json),
generated by `tools/audit_foreach_consolidation.py` from the locally available
65-benchmark source-preserving corpus.

## Existing mechanisms and their jobs

| Existing mechanism | What it does | Consolidated by `for_each`? |
|---|---|---|
| `Variable.expression.values` over an Object field | Projects a collected field into a Variable population. | Sometimes: only when the Variable solely transfers a scalar Item field into a dependent selector, with identical population/status/cardinality semantics. |
| `concat`, `regex_capture`, `split`, `substring`, arithmetic and conversion functions | Computes a new value or population. | No. These are legitimate computation and can be inputs to a later selector; an alias binding is not a replacement. |
| `unique`, `merge`, `count` | Deduplicates, combines, counts, or aggregates values. | No. Reduction over iterations is not value aggregation and must not erase duplicate/status semantics. |
| Object `Set` (`union`, `intersection`, `difference`) | Combines compatible Object populations. | No. `for_each` consumes one source population; it is not a set algebra replacement. |
| Object `Filter` | Applies a post-collection predicate while preserving collection semantics. | No. Moving it into a loop can change population, ordering, and completeness. |
| Named/shared Objects | Reuses one acquisition definition. | No. A source Object is required by `for_each`; shared Objects remain useful without expansion. |
| `Evaluate` Boolean and conditional branches | Combines Test outcomes and suppresses unselected branches. | No. Branch selection is not collection expansion. |
| Direct Variable used by several dependent Objects | Transfers one computed population to multiple consumers. | Usually no. Replacing it with several expansions duplicates lineage and may change shared acquisition. |

The key design boundary is **value computation versus Item correlation**:
`for_each` may replace a Variable that exists solely to move each collected
source Item's already-typed field into one dependent selector. It must not
replace a Variable that computes, aggregates, filters, deduplicates, or
changes the status/cardinality of values.

## 65-benchmark findings

The audit found these patterns in the 4,524 emitted Assessments:

| Finding | Count |
|---|---:|
| Variable definitions with direct `values: {object, field}` | 160 |
| Direct Object-derived Variables used by selector positions | 123 |
| Selector references from Object-derived Variables | 147 |
| Variables used solely to transfer an Object-derived value to selectors | 121 |
| Selector references for those sole-transfer Variables | 145 |
| Object-derived Variables not used by a selector | 37 |
| Object-derived Variables used both in selectors and elsewhere | 2 |
| Top-level `concat` Variables | 337 |
| Top-level `regex_capture` Variables | 90 |
| Top-level `merge` Variables | 54 |
| Top-level `unique` Variables | 24 |
| Top-level literal Variables | 1 |

The 121 sole-transfer cases are the only plausible consolidation pool. They
are not yet replacements:

* 97 cases have a direct-looking Test Object selector but retain
  `value_match`, which expresses population cardinality. Current `from` is a
  scalar lexical binding and has no approved equivalent for this cardinality.
* 24 cases occur in shared Objects, Set operands, or Filters. They require a
  separate proof that moving correlation to Object expansion preserves Set/
  Filter population semantics; the current contract does not admit a binding
  inside those positions.
* Some source fields are multi-valued or source Objects use filters/Sets. A
  per-Item loop can change duplicate handling, ordering, empty-population
  behavior, or incomplete-evidence propagation.
* The source-preserving corpus predates the current 0.4.1 proposal, so no
  candidate has an independent native 0.4.1 execution receipt.

Accordingly, the audit records **zero current `for_each` replacements proven
semantically equivalent**. This is a deliberate result, not a failure to
recognize the 121 patterns.

## YAML and Variable reduction

The defensible verified reduction is currently:

* **Variables removed: 0** — no candidate has a source-equivalence receipt.
* **YAML lines removed: 0** — no normalized rewrite is claimed equivalent.
* **Potential upper bound: 121 Variable declarations and 145 selector
  references**, if a future approved contract proves all sole-transfer cases
  equivalent. The source Object, selector binding, reducer, lineage, and
  evidence metadata still need authoring, so this upper bound is not a YAML
  reduction estimate.

The audit intentionally emits no line-count estimate for a non-admitted
rewrite. Adding `for_each` can increase a small Assessment's YAML while
reducing duplicated logic across many dependent checks; line count alone is
not a valid complexity metric. A future comparison must use parsed AST nodes,
source graph nodes, generated authoring bytes, and independently verified
outcomes—not a pretty-printer's line count.

## What could eventually be superseded

Subject to owner approval and a new 0.4.1 source-equivalence campaign, the
following narrow construct could be superseded:

> A local Variable whose expression is exactly `values(object, field)`, whose
> every use is one direct dependent Object selector, whose field is a typed
> scalar compatible with that selector, and whose old Variable population
> semantics equal one preserved iteration per source Item.

The replacement would be one named source Object plus one `for_each` dependent
Object per consumer, with an explicit reducer and complete lineage. This is a
candidate **authoring normalization**, not an instruction to delete the
Variable evaluator. The converter may choose either representation based on
source fidelity until equivalence is proven.

The following must not be removed:

* Variable functions and expressions that compute or aggregate values;
* Variables used in Requirements, Evaluate conditions, multiple unrelated
  consumers, or source-dependent transformations;
* Set/Filter semantics;
* named Object reuse independent of expansion; and
* source/provenance fields needed to reproduce OVAL 5.12.3 behavior.

## Proposed decision sequence

1. Re-run the audit on a current Tools 0.4.1 full-65 package and include all
   source Rules, not only the current emitted subset.
2. Select a bounded sample from the 121 patterns across Linux, Windows,
   Kubernetes, NGINX, and audit configurations. For each, compare original
   OVAL, current NG, and proposed NG using the same fixture populations,
   duplicate values, empty values, denied/error statuses, and incomplete
   evidence.
3. Resolve whether `from` may carry a typed cardinality qualifier or whether
   only scalar source Items are eligible. This is a normative decision, not a
   converter convenience.
4. Prove that Set/Filter and shared-Object placements have no changed
   population or status semantics before admitting them.
5. Measure AST/YAML/Variable complexity only for cases with independent
   equivalence receipts.
6. If the approved result is that a subset is redundant, define a deprecation
   period and source-fidelity escape hatch. Then coordinate exact changes to
   the canonical specification, Tools converter, VS Code editor metadata, and
   RI planner/evaluator in one versioned cascade.

No removal should occur before those gates. Issue #76's pending `for_each`
semantic decision remains the owner approval point, and this consolidation
review adds a second decision: whether any existing transfer idiom is actually
redundant after semantics—not merely syntactically similar.

## Normalized duplicate-Test census

The same corpus was also checked for repeated Test templates within one
Assessment. The deterministic normalization removes presentation title fields
(`test_title`, `object_title`, and `state_title`) and replaces Variable/OVAL
reference names with a marker before hashing. It found **63 duplicate template
groups containing 148 Tests**, with a syntactic upper bound of **85 Test
reductions**. This does not prove that Tests can share an Object, because the
normalization intentionally ignores names while source identity, acquisition
parameters, Set/Filter placement, status, and Result lineage remain material.
The receipt records `proven_same_source_transfer_groups: 0`; no Test is removed
or merged by this census.

## Correlated Require and cross-platform boundary

The existing field predicates do not yet define a source-alias operand. A
proposal such as `owner_uid: {from: source.uid}` requires canonical decisions
about lexical scope, exact datatypes, cardinality, missing fields, and status
propagation. It must be evaluated once per source Item and must preserve an
explicit zero-Item dependent population. It must never flatten dependent Items
or create a Cartesian product. Derived values such as
`home_dir + "/.ssh/authorized_keys"` remain Variable-based until a scoped
iteration expression is approved.

The selector audit covers all 101 supported capability mappings, including
Windows: 15 reviewed selector capabilities (28 fields), 62 selector-bearing
but unresolved capabilities, and 24 without selectors. Only the reviewed set
is executable for a binding. Experimental OVAL 6.0-derived mappings are
separately held (12 identified mappings) and are not part of OVAL 5.12.3
support or the 65-benchmark equivalence denominator.
