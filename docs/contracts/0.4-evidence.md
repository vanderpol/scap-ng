# Supplied evidence and storage fidelity

This supplements the [native evaluation contract](0.4-evaluation.md). It states evidence-preservation requirements independently of any database. The linked RI prototype is an implementation profile, not a new native wire format or collector.

## Existing native requirements

A Collection Result, its referenced Items and their typed field values describe different things. Preserve the Collection Result's status, logical/population completeness, ordered Item references, Item identity/capability/status, field names, scalar-versus-array shape, value order/duplicates, datatype/status, and full provenance/context. Omitted fields, empty arrays and explicit error values are distinct. Optional native information must be retained or explicitly rejected by a bounded implementation; it must not disappear during storage.

A successful storage operation is not collection completion or evidence authenticity. Staged, interrupted or incomplete collection cannot become complete merely because some rows exist. A reader must evaluate the authoritative population, not a truncated display or a partial page. A collection's error/incomplete state must not be hidden by successful Item comparisons. Unknown/error field values must not become known false comparisons that make `none` pass. Existing confirmed field absence is authored as standalone `values_found: none` on the individual field, without a comparator; the current RI still diagnoses that feature.

Variable values are not collected Items. Store resolved Variable audit records separately from acquisition evidence, preserving their status and typed ordered values. Such records are not permission to inject precomputed resolutions into evaluation or fabricate collected Items under Model A.

Binding is stronger than capability equality. Associate a Test with evidence for the same Object semantics and explicit execution context. Reuse must preserve schema/contract version, target/platform, snapshot/attempt, Variable/Input bindings, authoritative filter/projection, and trust/privilege context. Object IDs or a schema digest alone are not authenticity or cache-compatibility proof. No physical storage optimization may apply Require as a collection filter or remove evidence needed to determine authoritative counts.

## Four existing supplied-evidence profiles

These use the same equality/cardinality engine; storage adds no capability-specific evaluation code. The [fixture catalog](../../conformance/0.4/supplied-evidence.json) references eight immutable positive/negative teaching examples rather than copying them.

| Capability | Supplied field under test | Established complete-known comparison | Acquisition / other holds |
| --- | --- | --- | --- |
| `unix.file` | `owner_uid` (integer) | Exact integer equality; source `user_id` mapping. | No filesystem traversal, symlinks, ACL/time conversion or inaccessible-file acquisition. |
| `windows.registry` | `value` (integer in these fixtures) | Same-datatype integer equality; native value is polymorphic. | No registry traversal/view selection, access checks or inference of REG_* conversion. |
| `independent.shellcommand` | `stdout_line` (string) | Supplied string equality with independent field/Item quantifiers. | No command execution, exit/STDERR precedence, interpreter handling or adoption of OVAL-only signing/command restrictions. |
| `linux.rpminfo` | `architecture` (string) | Source `arch` mapping and supplied string equality. | No RPM database acquisition, EVR ordering, signature or package absence semantics. |

The [compatibility matrix](0.4-compatibility.json) records exact pinned OVAL Test/State/Item annotations and native datatype/name mappings for each profile. This establishes a bounded comparison mapping, not scanner or collection equivalence. Missing/error/incomplete propagation remains held where not established in the existing native contract.

## RI storage profile and trust boundary

The separate RI SQLite prototype uses a storage-independent raw-evidence cursor, explicit content/context binding and the same whole-Assessment validation/evaluator as supplied JSON. It enforces finite reads, record sizes, comparison budgets and deadlines. Source implementations are trusted adapter code responsible for immutable snapshots and unique Item IDs. Concrete memory/SQLite adapters enforce those properties; the evaluator additionally checks metadata, order/counts, status, field payloads and limits. An arbitrary malicious adapter is not sandboxed.

Target/context declarations and preserved provenance are claims by the producer, not cryptographic proof. Future collectors must derive bindings from a validated plan and actual execution context, enforce capabilities/projection/privilege, publish terminal completeness only after successful acquisition/storage, and attest evidence according to the deployment trust policy. This increment implements none of those collectors.

SQLite is gated to explicitly labeled synthetic evidence. Private file permissions are not encryption. Real sensitive evidence, key management, authenticated provenance, adversarial same-user tampering, hard filesystem quota/recovery and deployment-specific retention require further qualification/policy. The prototype neither installs a production scanner nor claims those protections solved.
