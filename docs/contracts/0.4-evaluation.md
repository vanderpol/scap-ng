# SCAP-NG 0.4 evaluation contracts

This normative addendum documents established native requirements and the owner's newly approved **Model A** contract. It does not amend the frozen JSON Schemas. The [compatibility matrix](0.4-compatibility.json) identifies exact source pointers and unresolved rules; implementers do not need OVAL to apply the rules below. [Executable fixtures](../../conformance/0.4/model-a/manifest.json) cover the approved complete-known-nonempty equality domain. Schema validity, language conformance and scanner qualification are separate claims.

## Variables — existing requirements and approved Model A

- A Variable has a name, `kind`, declared `datatype` and expression. A constant uses `literal`; a local Variable uses an admitted expression. Values must satisfy the promised datatype. No implicit caller-supplied resolution or hidden default is created.
- A literal list is ordered and preserves duplicates. A scalar and a singleton list supply the same one value. A reference supplies the referenced values and status; a same-datatype alias preserves the complete sequence, including order and duplicates. Cyclic or unresolved references cannot yield a successful value.
- A `variable.value` Test uses its named `variable` directly. It does not require an Object or host collection.
- **Model A:** a complete, known, nonempty Variable source is **one logical source group** whose `value` field contains all N typed values. Item existence sees one group; observed-field existence sees N values. An alias has the same grouping. Implementations MUST NOT split the list into N Items, deduplicate it, cast it, or invent collected Items, Item IDs or acquisition provenance.
- Model A is an evaluation view, not a canonical collected Item. A Variable result's `item_refs` identifies evidence consumed producing that Variable, not Items generated by its evaluation.
- Empty, error, unknown, incomplete and not-evaluated Variable results are outside this approved domain. Their precedence and resulting native outcomes remain unresolved; they MUST NOT be treated as a known nonempty value population or silently replaced with successful values.

## Comparisons and the three cardinality layers

All rules in this section apply to complete known nonempty populations and supported comparisons. Comparison operands are typed; no list-to-string conversion, zipwise equality, deduplication or truncation is permitted.

For each observed value, compare it separately with each expected value and apply `value_match` to those primitive comparison results. Apply `values_matching` to the resulting observed-value results. Apply the field condition as a whole to each logical source group/Item, then apply `items_satisfying` to those group/Item results. Existence controls are independent at their corresponding layer.

| Control | Counts or quantifies |
| --- | --- |
| `value_match` | Expected operand values matched by **one observed value**. Required where the schema admits an array, Variable reference or Organizational Input operand. |
| `values_found` | Observed values present in that field of one Item/source group. |
| `values_matching` | Observed values whose full comparison, including `value_match`, is true. |
| `items_found` | Authoritatively selected Items/source groups present. Model A supplies exactly one for a known nonempty Variable. |
| `items_satisfying` | Items/source groups satisfying the complete field condition. |

For a known nonempty population with N members and M successful comparisons: `none` means M=0; `exactly_one` means M=1; `one_or_more` means M>=1; `every` means M=N. Existence controls count present members rather than successful comparisons; `zero_or_more`, where admitted, imposes no additional count minimum. This is not an empty-population truth table or a reducer for unknown/error results. Field overrides apply at the field's scope; an implementation must not interchange these controls.

Examples: `[1,2] equals 1`, `values_matching: one_or_more`, `items_found: exactly_one` is true under Model A. `[1,1] equals 1`, `values_matching: exactly_one` is false because both duplicate values match. `[1,2] equals Variable([2,1])`, `value_match: exactly_one`, `values_matching: every` is true: each observed value matches one expected value; no positional pairing occurs. With `value_match: every`, that last field is false.

A false existence requirement remains false even if comparisons succeed. A false field condition can satisfy `items_satisfying: none`; do not collapse the field and Item folds into one Boolean check. An unsupported or indeterminate comparison is not a known false result that can make `none` pass.

## Datatypes

The declared datatype, field datatype and expected operand must be compatible under an established native contract. Same-datatype integer/string equality requires no coercion. Integer equality compares exact mathematical integers; spelling is not string equality, and implementations must not round through binary floating point. String equality compares the supplied string value without implicit trimming or case folding. Empty and Unicode strings are admitted by native grammar; the RI's current nonempty ASCII-only equality profile is a limitation, not a new native rule.

The native datatype vocabulary is broader than integer/string. Compatibility, cast rules and datatype-specific operators require their own contract and tests. In particular, this addendum does not authorize new float, version/EVR, date, record, case-insensitive or regex semantics. An implementation encountering an unsupported case must give an explicit diagnostic rather than silently convert it.

## Expressions and functions

| Native form | Established contract | Unresolved / RI boundary |
| --- | --- | --- |
| `literal` | Typed scalar/list/record shape; lists ordered, duplicates preserved. | RI supports bounded nonempty integer/string populations only. |
| `variable` | Resolve named values/status, preserving same-datatype aliases. | Broader datatype compatibility and indeterminate propagation need complete contracts. |
| `values` | Reads the named field of the selected Object. | Acquisition, field-absence and error/population behavior are not implemented by RI. |
| `concat` | Two or more ordered components; multiple values form a Cartesian product. Missing/error/incomplete statuses are not converted to string text. | Schema refers to inherited casting/status rules without a complete standalone table. Do not invent conversions or propagation. RI diagnoses the expression. |
| `regex_capture` | Apply the retained capture expression to input values; return its first capture according to the regex contract. | Regex dialect, edge cases and complete failure/status behavior need qualification. RI diagnoses the expression. |
| `unique` | Removes duplicate scalar values; it is an explicit transformation, not an implicit Variable operation. | Equality normalization/order guarantees outside established rules remain held. RI diagnoses the expression. |
| `merge` | Explicit values, delimiter, sort and order; no implicit deduplication. | Sorting/collation/casting/status details need qualification. RI diagnoses the expression. |

Other OVAL function names do not thereby become native syntax. The active native schema admits the seven forms above; the inactive migration candidate is not an additional runtime grammar.

## Evaluation and status boundaries

Native `evaluate` references Tests and admitted expression/group structures. A Test result is not a Definition/Assessment result. AND, OR, XOR and ONE have distinct schema-defined roles; ONE's exactly-one condition must not be implemented as XOR parity. The grammar's references to six-state evaluation do not supply every standalone propagation table. This increment implements no group or Definition roll-up and resolves none of those status holds.

Collection status/completeness, Item status, field status and Variable result status are different evidence. `complete` cannot be inferred from the mere presence of rows or values. Incomplete, error, missing and unknown evidence cannot be relabeled as complete, erased by a short-circuit, converted to a default scalar, or reported as an approved technical true/false result under this bounded contract. The exact native precedence among those states, empty populations, applicability and higher-level aggregation remains an owner decision where not already specified. An RI diagnostic has no technical outcome; it is not a canonical native error/unknown result implementation.

## RI implementation profile

The linked RI increment executes selected Tests over supplied complete known evidence and approved Model A constants/aliases. Its whole-document schema validation is mandatory. It uses exact integer and nonempty ASCII-string equality, explicit finite cardinality, request-local dependency caching, cycle detection, cooperative cancellation and resource limits. Expected Variable operands in this same domain use the shared comparison engine. No host acquisition, functions, new ordering/regex, empty/error/incomplete truth tables or Definition outcomes are enabled. API Test selection and implementation diagnostics are not new authoring syntax.

Storage is an adapter, not language semantics: preserving typed values, order, duplicates, identity, provenance and explicit completeness is mandatory regardless of in-memory or SQLite storage. Variable values remain separate from collected Items. Persistence may not fabricate source evidence or change evaluation results.
