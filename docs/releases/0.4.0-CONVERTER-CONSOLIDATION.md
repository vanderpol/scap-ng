# SCAP-NG 0.4.0 converter consolidation checkpoint

**Status: implementation work in progress, not native 0.4 migration parity.**
Tracks the owner decision of October 23, 2026: a single current converter
with the mature 0.3 OVAL functionality reused as shared infrastructure.
This document is engineering evidence, not a normative syntax change.

## Reuse rather than reinvent

| Existing asset | Correct ownership going forward | Proof/remaining boundary |
| --- | --- | --- |
| `tools/oval_semantic_ir.py` | Version-independent OVAL 5.12.3 parse, effective defaults, dependency closure and semantic accounting | Maintained focused parser checks; native 0.4 lowering separate |
| `tools/scap_upconvert_v003/` | Gradually factor proven source lowering, XCCDF binding, deprecated-test handling, native capability crosswalks into shared converter modules | Older code retained until each supported behavior is revalidated in 0.4 |
| `tools/scap_ng_roundtrip_v003/` | Maintain the source→semantic→OVAL comparator/regression corpus as cross-version evidence | A round trip is not proof of live scanner parity |
| Current `tools/v04_*` compiler and normalization code | Current native 0.4 renderer, schema validation, compiler and package verifier | Six-STIG authoring/bundle checks already pass; full OVAL behavior proof remains open |
| `tools/import_v04_oval_leaf_pilot.py` | Narrow independent two-shape original-OVAL source check, not the primary final converter | Keep as independent oracle until the shared-IR native adapter matches its output |

The final architecture is **OVAL 5.12.3 + SCAP 1.4/XCCDF → shared semantic
IR → version-specific native 0.4 renderer → 0.4 schema → `.scapng` compiler**.
This retains a single maintained source tree; it does not create another
0.3 release branch. Historic 0.3 outputs remain reproducible from immutable
refs/assets, not routinely regenerated from current `main`.

## First verified shared-core preservation gate

`tools/test_oval_semantic_core_preservation.py` explicitly reuses the mature
`oval_semantic_ir.parse` on three pinned in-repository OVAL sources:

- Original OVAL Set/Filter source: default `set_operator=UNION`, default Filter
  `action=exclude`, filter-before-set semantics and a retained `var_check=only
  one` value quantifier.
- 0.3 stress source: cross-product arithmetic from two constant Variables
  produces six ordered values, and dependent `count` produces six.
- Current original OVAL 0.4 logic-scope fixture: all six Definitions preserve
  their Test `state_operator` values, including OR, ONE and XOR. Mutating a
  State reference yields an explicit unresolved-reference diagnostic.

These focused tests demonstrate **existing parser/semantic-IR capabilities**
we must not discard. They do **not** demonstrate that all three cases have
been converted to native 0.4 or evaluated by a scanner.

## First implemented cross-version converter adapter (two fixtures)

`tools/scap_converter_core.py` now uses `oval_semantic_ir.parse` and the
established `scap_upconvert_v003` Definition lowering and capability mapping
to produce an aligned 0.3 graph. It then explicitly projects two reviewed
source shapes to 0.4, using the existing invertible flat-Object and Test
requirement transformations. The 0.4 compiler checks each Test. Finally the
candidate must agree in all executable fields with the **separate** 0.4
original-OVAL importer, after invertibly flattening that importer's old
Object syntax. A mismatch is an error, not a warning.

The five new integration tests confirm both positive source shapes, schema
and native Test-program acceptance, independent native OVAL export, rejection
of six semantic/source mutations, rejection of a deliberately corrupted 0.3
lowering, and the public CLI/evidence contract. The `0.4 shared converter
core regression` workflow runs these tests. See the
[developer runbook](../developer/CONVERTER-COMPILER-RUNBOOK.md).

This **demonstrates reuse**, not broader conversion coverage: exactly the
same two leaf shapes as the independent pilot are currently admitted; old
0.3 support is retained for expansion. The adapter emits single Assessment
authoring JSON, not a closed or scanned `.scapng` package.
The 0.3 capability mapping catalog must be present: it rewrites native 0.3
quantifiers and creates a single-UNION wrapper around the shell direct Filter.
The adapter checks and eliminates only that source-proven synthetic wrapper,
not genuine original OVAL Sets. GitHub's full-checkout CI caught this
dependency after an incomplete sparse local checkout gave a false green;
focused tests now run locally against both mapping directories as well.

## Next implementation gates (issue #232)

1. Extend the now-wired shared IR and 0.3 source lowering into a stable
   converter-facing API without deleting old code or disrupting current CI.
2. Extend the native 0.4 projector beyond the two strict leaf examples.
   Compare original source, shared-IR output, native JSON/YAML, regenerated
   OVAL and a compiled closed graph where applicable.
3. Extend by real constructs (criteria nesting, Variables/function chains,
   Sets, Filters, records, operators, and multi-Test logic). Preserve source
   identity/provenance separately, apply 0.4 syntax changes only after a
   semantic-equivalence proof, and fail closed when a construct lacks one.
4. Run existing 0.3 OVAL round-trip fixtures against the shared core and
   native 0.4 stage. Report **denominator, supported, blocked, and unproved**
   separately; never infer coverage from a compiled bundle alone.
5. After focused positive/negative tests, run maintained small STIG checks;
   save the six-STIG integrated run for a deliberate release checkpoint.

Do not delete old pathways or label a full corpus equivalent merely because a
new parser accepts the input. Deprecation rules and the six-state result
semantics remain unchanged unless separately accepted by human review.
